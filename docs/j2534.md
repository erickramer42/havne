# J2534 transport

How the Windows J2534 Pass-Thru stack works today. Why it is built
this way is covered in ADRs [0007](adr/0007-uri-selected-transports.md)
through [0012](adr/0012-j2534-transport-adoption.md), and
[0014](adr/0014-single-threaded-surrogate.md) for the surrogate's
current shape. For what has
been verified and what hasn't, see [STATUS.md](../STATUS.md) and
[testing.md](testing.md).

**Verification level: HARNESS, BENCH and one vehicle.** Everything below
has been exercised end to end against the in-tree fake vendor DLL,
both same-arch and cross-arch (x64 app → x86 surrogate → x86 fake).
Discovery has also run against real installed drivers (OBDX Pro VT
and VX), and the OBDX Pro VX itself has been loaded and connected
through the surrogate in a formal bench session (2026-10-16, USB
power, no vehicle: vendor open status 0, the 8-byte flow-control
filter shape accepted, clean teardown). An informal 2026-10-20
session confirmed the 4-byte shape that replaced it (logged vendor
status 0) and the fault path on the same adapter
([bench note](bench-sessions/2026-10-20.md)). A 2026-10-22 run took
the current build through the requests-failing and quiet states with
recording on, and measured the VX's read, write and timestamp
behavior ([session sheet](bench-sessions/2026-10-22.md)). The first
read-only vehicle session, the same evening, ran the `obd2` scheduler,
`?poll=` and the supported-PID bitmaps against a car's engine ECU
through the VX ([vehicle session](bench-sessions/2026-10-22-vehicle.md)).

## Layers

```

        │  ecuio_j2534_* loader helpers (internal.h)
        ▼
j2534_loader.cpp           discovery, PE sniff, backend routing, in-proc vendor calls
        ├── in-proc:   LoadLibraryEx → vendor DLL (x64)

```

## URI grammar

```
j2534://[<selector>][?<param>=<value>[&<param>=<value>...]]
```

**Selector:**

| Form | Resolves to |
|---|---|
| *(empty)* | The first discovered device |
| `<vendor-name>` | A discovered device whose name matches, case-insensitively |
| A path ending in `.dll`, or containing `\` or `/` | A direct load. Tests and development use this to reach the fake. |

**Query parameters:**

| Key | Value | Notes |
|---|---|---|
| `baud` | Decimal, nonzero | Default is the ISO 15765 rate of 500 kbit/s. |
| `flags` | `0x`-hex or decimal; 0 allowed | Passed to `PassThruConnect`, with `CAN_29BIT_ID` (0x100) added when the channels use 29-bit IDs. A channel table mixing 11- and 29-bit IDs would need `CAN_ID_BOTH` and is rejected at create. Other bits aren't interpreted. |
| `filter` | CAN ID 1–`0x1FFFFFFF` | Receive ID. Registers a `FLOW_CONTROL` filter. |
| `txid` | CAN ID 1–`0x1FFFFFFF` | Transmit ID. Default is the profile's declared transmit ID, else `0x7E0`. |
| `poll` | PID `0x00`–`0xFF` | Single-PID Mode-01 request loop. `0x00` is the supported-PIDs bitmap for PIDs 0x01–0x20. Replaces the profile's PID rotation: no scheduler is built. Needs a channel, from `?filter=` or the profile's declarations, so `?profile=raw&poll=` alone fails while `?profile=raw&filter=0x7E8&poll=` and a bare `?poll=` under `obd2` work. |
| `profile` | Name, 1–63 chars | ADR-0013 profile override. Core validates it in `ecuio_session_create` before the transport attaches, so this parser accepts it as is. |

Parsing is strict. The query grammar is the one every scheme shares
(`core/src/uri_query.h`; `mock://` accepts only `profile`). Each of the
following returns `ECUIO_ERR_BAD_URI` from `ecuio_session_create`,
before any DLL is loaded, and `ecuio_last_error_detail` names the key
and what it should hold:

- unknown or uppercase keys
- a segment with no `=`
- empty segments, a trailing `&`, or a bare trailing `?`
- non-numeric values, `baud=0`, or out-of-range IDs or PIDs
- `poll` with no channel from either `?filter=` or the profile. This
  check runs at attach rather than in the parser, because it needs the
  profile's declared channels, but attach still runs before the DLL
  loads.

If a key appears twice, the last occurrence wins. A selector that
matches no installed adapter is `ECUIO_ERR_NO_TRANSPORT`, and an
unknown `?profile=` name `ECUIO_ERR_UNKNOWN_PROFILE`.

**Profile-declared channels (ADR-0013 §4).** When the URI carries no
`?filter=`, the transport derives its channel table from the profile's
signal set at attach — before the device opens — registering one
flow-control filter per channel and routing scheduler requests to the
channel that owns each PID. The `obd2` set declares `0x7E0`
(transmit) / `0x7E8` (receive), so a bare `j2534://` URI starts and
streams with no query parameters.

**Coupling rule.** A request loop, scheduled or `?poll=`, needs at
least one channel to receive on. The check fires at attach, before
any hardware is touched, so it never costs a device open. For
`?poll=` it bites under `raw` without `?filter=`. For the scheduler,
shipped profiles declare channels, so that arm is reachable only by a
future profile author omitting them.

**Example URIs:**

- `j2534://<dll>` — bare: obd2 default, filter on 7E8, requests to 7E0, scheduler active
- `j2534://<dll>?txid=0x7DF` — broadcast requests to 7DF, still filtering 7E8 responses
- `j2534://<dll>?profile=raw&filter=0x7E8&poll=0x0C` — single-PID poll loop, log only. `?filter=` supplies the channel `raw` lacks; without it, create fails.
- `j2534://<dll>?poll=0x0C` — single-PID poll loop under the `obd2` default: only PID 0x0C is requested, on the derived channel, and its signals still decode
- `j2534://<dll>?profile=raw` — no decode, no filter (verbatim passthrough). A real ISO 15765 channel with no filter receives nothing, so add `?filter=` to hear an ECU.
- `j2534://<dll>?profile=obd2` — explicitly selects obd2 with its channel declarations

## Session lifecycle

| Session call | Transport work |
|---|---|
| `ecuio_session_create` | Resolve the URI, then derive the channel table and, unless `?poll=` is set, the PID scheduler from the profile's signal set. No hardware is touched yet, and the request-loop-without-channel check fires here. Then `ecuio_j2534_open` (load and route the DLL, then PassThruOpen — in surrogate mode, via OP_OPEN after the pipe handshake), then `PassThruConnect` (ISO 15765). Failures surface here, each with its code and its words in `ecuio_last_error_detail` ([below](#why-a-connect-failed)). Last, the session info ([below](#what-a-session-runs-on)): `READ_VBATT` and `PassThruReadVersion`, neither of which can fail the connect. |
| `ecuio_session_start` | Register one `FLOW_CONTROL` filter per channel — a mid-loop failure unwinds the filters already registered (the channel stays connected until close), and a refused filter returns `ECUIO_ERR_VENDOR_REFUSED`. Then start the worker. |
| Worker loop | One of three modes, fixed at start. **Scheduler** (a set with Mode-01 defs, those keyed by a 2-byte `41 <PID>` at payload offset 0, such as `obd2`; `ecuio_mode01_pid` decides): each 100 ms cycle writes one Mode-01 request for the rotating PID to the channel that owns it, then drains `ReadMsgs` (20 ms timeout, at most 10 reads, the first empty read ends the drain, leftovers carry into the next cycle), then sleeps the remainder against an absolute deadline so drain cost can't drift the cadence. **Poll** (`?poll=`): one request to the channel that owns the PID (channel 0 when no def claims it), one 100 ms read, a 100 ms sleep. `?poll=` outranks the profile, so no scheduler is built. **Passive**: one 100 ms read, a 20 ms sleep. Both request modes keep writing while the link is hard-failed or requests are failing, because each request is the recovery probe; the backoff replaces the normal sleep. |
| `ecuio_session_close` | Join the worker → stop every channel's filter (best-effort) → `PassThruDisconnect` → `PassThruClose` → `FreeLibrary`, or the surrogate's shutdown path |

**The teardown order is a hard contract.** The worker calls vendor
functions through pointers, and those pointers dangle the moment the
module unmaps. In surrogate mode the worker is joined before the
client's polite-shutdown and job-kill path runs.

**Receive framing.** ISO 15765 messages carry a 4-byte big-endian address header
in-band.
- *With channels,* the worker checks the 4-byte header against every
  channel's receive ID, strips it on a match, and stamps
  `arbitration_id` with that channel's ID. Non-matching frames are
  dropped but still consume read budget (bounds loop time).
- *Without channels (raw profile),* frames are dispatched verbatim
  with `arbitration_id = 0`.

**Frame time.** A frame's `timestamp_us` is microseconds since attach
(the end of `ecuio_session_create`), as on `mock://`. The vendor
stamps each message from a 32-bit microsecond clock that wraps every
71.6 min and starts anywhere (the VX's keeps running across
connects), so the worker maps it (`core/src/j2534_clock.h`):

- the first frame takes the host's time since attach, as it reaches
  the worker;
- each later one adds the vendor's delta since the one before, which
  keeps the adapter's resolution, frames from one batch included;
- the host's elapsed time decides how often the vendor clock wrapped
  in between, so a gap longer than 71.6 min still counts in full;
- a vendor delta more than a minute ahead of the host's is a clock
  that stepped (backwards, or a reset), and the host's delta stands
  in.

The result never decreases. Every delivered frame advances the clock,
dropped ones included. Both backends hand the worker the vendor's stamp
as it came, and the session log's `OP_READ frame` lines keep it raw.

**Read status.** Both backends map the vendor's `ReadMsgs` result the
same way:

| Vendor result | Transport sees |
|---|---|
| `STATUS_NOERROR`, no messages | No frame |
| `ERR_BUFFER_EMPTY` (0x10), no messages | No frame |
| `ERR_TIMEOUT` (0x09), no messages | `ECUIO_ERR_VEHICLE_TIMEOUT` |
| Any other status, no messages | `ECUIO_ERR_TRANSPORT_HARD_FAILURE` |
| `STATUS_NOERROR` or `ERR_TIMEOUT`, messages returned | The messages are delivered (in-proc one per call, the surrogate as a batch) |
| Any other status, with a nonzero count | The count is ignored, and the row for that status with no messages applies |
| Surrogate: pipe transaction fails, or a response claims more than 16 frames | `ECUIO_ERR_TRANSPORT_HARD_FAILURE` |

Delivering under `ERR_TIMEOUT` is deliberate: a conforming vendor
returns it together with a short batch. Under any other status the
count isn't trusted, because a vendor may leave `pNumMsgs` (and the
buffer) untouched on error. The VX did exactly that on a failed write
("status 7, written 1"). Trusting such a count produces phantom frames
that read as healthy: the surrogate's static read batch would replay
the previous read, and in-proc a zeroed message would dispatch. Both
backends share one rule, `ecuio_trusted_count` in `j2534_ptypes.h`.
`ERR_BUFFER_OVERFLOW` (0x12) isn't on its list, so an overflow read
drops its batch and counts as a hard failure.

Indications aren't frames, and both backends skip them
(`ecuio_pt_is_indication` in `j2534_ptypes.h`): a message with
`TX_INDICATION` or `TX_MSG_TYPE` in `RxStatus` (a transmit-done
indication or a loopback echo; the VX queues one after every write),
and the `START_OF_MESSAGE` indication a vendor queues when a segmented
ISO 15765 reply starts arriving, ahead of the whole message. Skipping
one doesn't end the read: in-proc, the loader reads again with what's
left of the timeout, and the child does the same with a batch that
held nothing but indications. So a reply queued behind its request's
indication comes back from the same read, and the worker's drain goes
on past it. A read skips at most 16; past that it's judged like an
empty read.

**Link health.** The worker publishes the session's `last_error` and
`error_count` (`ecuio_session_get_error_state`). Each read is judged
in this order, first match wins:

1. **Hard read failure**, meaning any status other than `ECUIO_OK` and
   the vehicle-timeout mapping: `ECUIO_ERR_TRANSPORT_HARD_FAILURE` at
   once. The transition counts one episode in `error_count` and starts
   the backoff at 100 ms; a hard read after a clean one ended the
   backoff starts it again, in the same episode. This outranks
   everything below, including a failing write.
2. **Latched write failure:** while the last write failed, no other
   read moves the state.
3. **Matched frame** (its header matches a channel and it was
   dispatched, or any frame when there are no channels): `ECUIO_OK`. The
   backoff and the quiet count clear.
4. **Unmatched frame** (delivered, but its header matches no channel):
   the adapter is reading the bus, so a hard failure ends and the
   backoff clears. But the frame isn't a reply to us, so the state
   becomes `ECUIO_ERR_VEHICLE_TIMEOUT`, with no episode. This skips the
   quiet debounce.
5. **Quiet** (an empty read, `NOERROR` or `ERR_BUFFER_EMPTY`, or
   `ERR_TIMEOUT`): the adapter answered, so the backoff clears at
   once. Ten in a row (about 1 s in scheduler mode) set
   `ECUIO_ERR_VEHICLE_TIMEOUT`. A single empty read never does, because
   every drain ends on one. Clearing the backoff first matters after a
   hard failure: the debounce then counts reads at the request
   cadence, where one read per backoff interval would take about 26 s.

Writes are judged separately. A write fails when the vendor's status
isn't `STATUS_NOERROR`, or when it is but the vendor reports no
message written: a success for a message never sent. A failed write
latches and, unless a
hard read failure already holds, sets `ECUIO_ERR_REQUEST_FAILED`: one
episode on the transition, backoff from 100 ms. Only a successful
write clears the latch. It returns `ECUIO_ERR_REQUEST_FAILED` to `ECUIO_OK`
without waiting for a reply, because a write accepted after a
failure means the adapter could send again. On a fresh connect an
accepted write proves less: the VX accepts three frames with nothing
on the bus to acknowledge them, fails the fourth, and on that bench
accepted no other until the next connect
([bench 2026-10-22](bench-sessions/2026-10-22.md)). This is the
no-ACK bus: nothing on the bus acknowledges, so reads stay clean while
writes fail, and it reads as "requests failing" rather than an adapter
fault. It takes an adapter on no live bus, or a bus that's fully
asleep. On the first vehicle the bus acknowledged every frame with
the ignition off, so the ignition-off car read as quiet
([vehicle 2026-10-22](bench-sessions/2026-10-22-vehicle.md)).

The backoff doubles after each slept interval, up to 5 s, for as long
as a failure persists. Both request modes keep writing throughout,
because each request is the recovery probe.

HARNESS tests cover the health machine on both backends: each
`J2534HealthTest` case runs once in-proc and once through the
surrogate (`HardFailureSetsCanonicalErrorAndRecovers`,
`QuietBusDebouncesToVehicleTimeoutWithoutEpisode`,
`UntouchedCountUnderHardErrorReportsUnhealthy`,
`WriteFailureLatchesRequestFailedAndClears`,
`HardReadFailureOutranksRequestFailed`,
`UnmatchedDeliveredFrameGoesQuietNotHealthy`,
`BackoffGrowsUnderSustainedHardFailure`). The bridge polls this state
on its 100 ms coalesce tick, publishes it as `linkState`, and logs
transitions to the Settings activity log. The header pill, LiveView
(banner), the Home status card, the Dashboard header and the Settings
connection label show it (Known Issue #11):

| Code | `linkState` | What the user sees |
|---|---|---|
| `ECUIO_OK` | `ok` | No banner; green Home dot and Settings label |
| `ECUIO_ERR_VEHICLE_TIMEOUT` | `quiet` | Amber "Vehicle not responding — quiet bus" |
| `ECUIO_ERR_REQUEST_FAILED` | `requests` | Amber "Requests failing — check the vehicle connection and ignition"; log line "Link: requests failing (N episode(s))" |
| `ECUIO_ERR_TRANSPORT_HARD_FAILURE` | `fault` | Red "Adapter fault — N episode(s), retrying with backoff" |
| Any other code | `degraded` | Red "Link degraded (error N)", forward-compatible |

`QtTuneBridge::linkStateForError` holds the mapping, and
`BridgeTest.LinkStateMapsEveryPublishedCode` pins it.

### Why a connect failed

`ecuio_session_create` and `ecuio_session_start` return a code for the
cause, and `ecuio_last_error_detail` says it in words, per thread
([ADR-0018](adr/0018-connect-failure-reporting.md)). The bridge shows
both in the Settings error line and the activity log.

| Code | Cause | Detail, for example |
|---|---|---|
| `ECUIO_ERR_BAD_URI` | Malformed query or value; `?poll=` with no channel; channels mixing 11- and 29-bit IDs | `?baud= needs a nonzero decimal, not '0'` |
| `ECUIO_ERR_UNKNOWN_PROFILE` | `?profile=` names no registered profile | `no profile is named 'bogus'` |
| `ECUIO_ERR_NO_TRANSPORT` | No installed adapter matches the selector, or none is installed | `no installed J2534 adapter is named 'X'` |
| `ECUIO_ERR_LOAD_FAILED` | The DLL won't load, or lacks a mandatory export, in-proc or in the surrogate (exit 4 or 5) | `couldn't load the DLL (Windows error 126)` |
| `ECUIO_ERR_VENDOR_REFUSED` | `PassThruOpen`, `PassThruConnect` or a filter returned a vendor status, or `PassThruOpen` never returned | `PassThruOpen returned status 34 (vendor-specific): <vendor text>` |
| `ECUIO_ERR_SURROGATE_FAILED` | No surrogate exe, a failed spawn or handshake, a surrogate from other shared headers, or one that stopped answering | `the surrogate was built from other shared headers: rebuild build-win32, then build` |

A refused call is named with its status, by its J2534-1 v04.04 name
or as vendor-specific, and the vendor's text from
`PassThruGetLastError` follows when the DLL exports it. Both backends
produce the same words: in-proc the loader asks the DLL, and through
the surrogate the client asks the child (`OP_GET_LAST_ERROR`) before
closing it.

### What a session runs on

`ecuio_session_get_info` copies out what a session connected to
([ADR-0019](adr/0019-session-info.md)): the backend and the DLL's
architecture, the protocol, baud and connect flags, the profile and
its channels, and two readings the adapter may give, its battery
voltage (`READ_VBATT`) and its firmware, DLL and API versions
(`PassThruReadVersion`). Attach fills it after `PassThruConnect`;
nothing changes it afterwards.

Both readings are device calls, made once. A refusal, or a DLL without
`PassThruReadVersion`, leaves its flag clear (`ECUIO_SESSION_INFO_VBATT`,
`ECUIO_SESSION_INFO_VERSIONS`) and the connect succeeds. The export is
optional on both backends; through the surrogate it travels as
`OP_READ_VERSION`. Each version string is cut at 79 characters and put
on one line, alike on both backends.

The bridge logs it after "Connected:", and a recording's `events.log`
keeps it:

    Session: x86 DLL, through the surrogate; ISO 15765 at 500000 baud; profile obd2, channel 0x7E8/0x7E0 (rx/tx); battery 13.8 V; firmware fake-fw 1.0, DLL fake_j2534 0.3, API 04.04

That is the Win32 fake's line. A refused reading reads "no battery
reading" or "no version reading".

## Discovery

`ecuio_j2534_discover_devices` makes four registry sweeps (two roots
× two WOW64 views) and removes duplicates by DLL path plus vendor
name. Duplicates arise because the views overlap.

- **Roots:**
  - `SOFTWARE\Pass-Thru Support.04.04`, the name the spec uses
  - `SOFTWARE\PassThruSupport.04.04`, without the hyphen, as written
    by real installers (OBDX Pro, under `WOW6432Node` only)
- **Views:** `KEY_WOW64_64KEY` and `KEY_WOW64_32KEY`. These are flags,
  not a hard-coded `WOW6432Node` path, so the sweep works from a
  process of either bitness.
- **Per vendor:** reads `FUNCTIONLIBRARY` (expanding `%VAR%`
  references when the value is `REG_EXPAND_SZ`) and annotates the
  DLL's PE architecture in `reserved[0]`: 1 = x86, 2 = x64, 0 = unknown.
- **Text is UTF-8.** The registry is read through the UTF-16 (`W`)
  calls and converted, so `vendor_name` and `dll_path` are UTF-8, and
  so is a path in a `j2534://` URI. The loader, the PE sniff and the
  surrogate pass paths to Windows as UTF-16, so a non-ASCII install
  path loads (`FakeFixture.NonAsciiDllPathLoadsInProc`,
  `J2534SurrogateTest.NonAsciiDllPathLoadsInTheChild`). A path whose
  UTF-8 form doesn't fit `dll_path` (256 bytes) isn't listed. The
  registry half has no automated test: it would need an HKLM entry.

The bridge exposes the result as `discoverJ2534Devices()`, a list of
`{vendorName, dllPath, architecture}` entries for the Settings-page
picker. Each registry entry is treated as one device (Known Issue
#13).

## Loader and routing

`ecuio_j2534_open` reads the PE machine field once and picks a
backend ([ADR-0009](adr/0009-pe-architecture-routing.md)):

| Machine type | Backend |
|---|---|
| x86 | Surrogate |
| x64 | In-proc |
| Unknown | In-proc, so the honest load error survives |

Both backends resolve the same nine mandatory exports: `PassThruOpen`,
`Close`, `Connect`, `Disconnect`, `ReadMsgs`, `WriteMsgs`, `Ioctl`,
`StartMsgFilter` and `StopMsgFilter`. A missing export unwinds through
a single failure site, so no `HMODULE` leaks.

These helpers each forward on `is_surrogate`:
- `ecuio_j2534_connect_channel` / `disconnect_channel`
- `read_frame` / `write_frame`
- `ioctl`
- `start_msg_filter` / `stop_msg_filter`
- `inject_test_frame` (test only)

`ecuio_j2534_backend_name()` reports `"inproc"` or `"surrogate"`.

## Surrogate

[ADR-0008](adr/0008-x86-surrogate-host.md) covers the original design
and [ADR-0014](adr/0014-single-threaded-surrogate.md) its current,
single-threaded shape. This section is the operational detail.

**Spawn.** The client opens the session log, finds the exe, and
creates the pipe and the job object. It then launches
`ecuio-j2534-surrogate.exe <dll> <pipe>` suspended, inside a
`KILL_ON_JOB_CLOSE` job object. **The child connects the pipe
FIRST**, then loads the DLL, resolves its exports, and performs
`PassThruOpen` only when `OP_OPEN` arrives — inside the request loop.
The handshake times out after 8 s (`ECUIO_SUR_HANDSHAKE_MS`
overrides; test knob).

**Build fingerprint.** The client and the child compile the shared
headers in separate trees, so each carries `ECUIO_SUR_FINGERPRINT`,
32 bits of a SHA-256 over `j2534_ptypes.h` and `surrogate_protocol.h`
that the configure step generates (`generated/ecuio/sur_fingerprint.h`).
`OP_OPEN` carries the client's. A child with a different one answers
`STATUS_FAILED` without calling the vendor, and every child echoes its
own in the reply, which the client checks as well, so a child built
before the check is caught too. Either way the open fails with
`ECUIO_ERR_SURROGATE_FAILED`, and the session log names both values.

- **The exe** is the one next to the running app, or
  `ECUIO_SURROGATE_EXE`. The variable only relocates the surrogate:
  it must be an absolute path to an existing file named
  `ecuio-j2534-surrogate.exe`, or the open fails with the reason in
  the session log (`J2534SurrogateTest.SurrogateExeOverrideIsRestricted`).
  The spawn line names the exe and says when it came from the
  variable. The exe is passed as the application name, so
  `CreateProcess` never searches for it.
- **The pipe** is `\\.\pipe\ecuio-j2534-<pid>-<seq>-<32 hex>`, the hex
  from `BCryptGenRandom`. It is created with
  `FILE_FLAG_FIRST_PIPE_INSTANCE` (an existing pipe of that name fails
  the open rather than being joined), `PIPE_REJECT_REMOTE_CLIENTS`, one
  instance, and a DACL granting the current user alone. The default
  DACL would let any local user open it for reading, enough to take
  the only instance before the child.
- **Handles:** the child inherits the session log and nothing else.
  A `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` names that one handle; without
  it, inheritance would pass every inheritable handle in the app. The
  client clears the log's inherit flag right after the spawn.
- **Text:** the DLL path reaches the child as UTF-16 (`wmain`), so a
  non-ASCII path loads there too.

**Session log.** Each session has one log file holding both halves:
the child's stdout/stderr and the client's own lines.
- **Where:** `%TEMP%\ecuio-surrogate.log`. Each spawn takes that
  name and keeps the log it replaces as
  `ecuio-surrogate.<YYYYMMDD-HHMMSS-mmm>.log`, named after the old
  log's last write (local time); the newest 50 are kept, and a suite
  run spawns dozens. A session that starts while another holds that
  file gets
  `%TEMP%\ecuio-surrogate-<pid>-<n>.log` instead of running without
  a log. `ecuio_j2534_sur_log_path()` returns the session's path
  (UTF-8), and the client's second line names it.
- **Stamps:** both sides stamp local wall-clock time
  (`HH:MM:SS.mmm`), so the file reads as one timeline. Each side
  writes whole lines in one call, so lines never splice. Child lines
  start `[surrogate `; client lines start `[sur `.
- **The child logs** each startup stage, and the vendor status of
  every `OPEN`, `CONNECT`, `DISCONNECT`, `IOCTL`, `START_FILTER` and
  `STOP_FILTER`. It logs `OP_WRITE` when its status or written count
  changes, and `OP_READ` when its status changes or frames arrive, so
  expect about 10 lines/s while an ECU answers.
- **Payloads, opt-in:** with `ECUIO_SUR_LOG_FRAMES=1` in the app's
  environment (the child reads it once, at spawn), the child
  also logs every message it writes and every one the vendor returns,
  before anything is dropped or stripped. The bytes include the 4-byte
  CAN ID, so a reply with 4 data bytes is `len 8`. Set it at launch,
  or tick Record sessions in Settings, which sets it for the spawns it
  records unless it was set at launch
  ([ADR-0017](adr/0017-session-recording.md)):

  ```
  OP_WRITE frame: status 0, tx 0x00000040, len 6: 00 00 07 E0 01 0C
  OP_READ frame: status 0, rx 0x00000000, ts 4097, len 8: 00 00 07 E8 41 0C 1F 40
  ```

  Indications are logged too, marked "(indication, not delivered)".
  Bytes past 64 are counted (`+N`), not shown. It adds about two lines
  per request cycle. The in-proc backend has no session log, so an x64
  vendor DLL gets no payload capture.
- **The client logs** the spawn first (child pid, surrogate exe, DLL,
  then the log path), written while the child is still suspended.
  After that it logs only trouble:
  - a rejected or missing surrogate exe, a failed pipe or job setup,
    or a failed CreateProcess, naming the exe;
  - a handshake timeout;
  - a blocked `OP_OPEN` (no reply, child alive), and the child's
    decoded exit code;
  - a refused `PassThruOpen` or `PassThruConnect`, with the vendor
    status;
  - transaction failures and desyncs;
  - a skewed reply (`num_frames` or ioctl `data_len` past the wire
    limit);
  - frames dropped with a late `OP_READ` reply (below).
- **stderr:** the client also writes its lines to the app's stderr,
  but a GUI launch needs no redirect to keep them.

**Late replies.** When a transaction times out, the client remembers
its request ID. Before the next request, it reads and discards that
late reply, so the next request isn't paired with it. If the late
reply was an `OP_READ`'s, its frames are dropped with it, and the
client logs `drain_pending: dropped N frame(s)`. Getting there takes a
read the child answers more than 500 ms past its own timeout.

**Unresponsive children.** If the late reply doesn't arrive within that
next request's timeout either, the child is wedged, not slow: the
client logs `child unresponsive` and every later transaction fails at
once. Without that, a teardown would pay a full 3 s per filter, for
the disconnect and for the close. Close then kills the child through
the job object without waiting for a polite exit. A disconnect from a
wedged child costs about 6 s at worst: the timeout in flight plus the
one that marks the child unresponsive.

This ordering makes the wire itself the diagnostic:

- Handshake times out, child alive → the child never opened the
  pipe; process startup stalled before any vendor code ran.
- Pipe connected → the child started. It hasn't loaded the DLL yet.
- Child exits before answering `OP_OPEN` → its exit code names the
  stage: 4 (the DLL didn't load) or 5 (an export is missing).
- `OP_OPEN` answered → the DLL loaded and all nine exports resolved.
  Then either the fingerprints differ ("built from other shared
  headers", and the vendor was never called), or `PassThruOpen`
  returned: a device ID, or a refusal with the vendor status. After
  either failure the client shuts the child down.
- `OP_OPEN` unanswered, child alive → the vendor is blocked in
  `DllMain` or `PassThruOpen`, typically waiting for absent hardware.
  `OP_OPEN` gets its own handshake window. On timeout the client
  terminates the child, because a single-threaded child stuck in
  vendor code can't answer `OP_SHUTDOWN`. Only a reply that *timed
  out* counts as blocked. A broken pipe means the child is exiting
  with code 4 or 5, so the client waits for the exit and decodes it.
  Checking only whether the child is alive would race the moment
  between the pipe closing and the process ending, and log a failed
  load as a blocked vendor.
- A failed handshake cancels the pending `ConnectNamedPipe` before the
  client releases its event and pipe.

**One thread, one request at a time** ([ADR-0014](adr/0014-single-threaded-surrogate.md)).
The child reads a request, makes at most one vendor call, writes the
response and loops, so vendor calls are serialized by construction
and no lock exists. The vendor status in each response is data: a
refused ioctl, a failed filter stop or an empty read is answered and
the loop continues. Only `OP_SHUTDOWN` or a broken pipe ends it,
after which the child disconnects any open channel, closes the
device and unloads the DLL. A successful `OP_DISCONNECT` clears the
channel, so teardown never disconnects twice. Whether a device and a
channel are open is tracked with explicit flags, not by treating ID 0
as "none": J2534 doesn't reserve 0. A vendor call that never
returns leaves the child hung; the client's transaction times out,
and the kill-on-close job reaps the child at close.

**Child exit codes.** These are the first thing to check when a spawn
fails. The client decodes the code into the session log
(`open: child exited with code N (...)`). On exit 5 the child's lines
names every missing export, so the log alone identifies the gap;
`dumpbin /exports` remains the cross-check for x86 name decoration.

| Code | Stage that failed |
|---|---|
| 1 | Argument count |
| 2 | Retired (attached the shared ring before ADR-0014). Not reused. |
| 3 | Retired (mapped the ring view and event before ADR-0014). Not reused. |
| 4 | `LoadLibrary` of the vendor DLL |
| 5 | A mandatory export is missing (on x86, check export name decoration) |
| 6 | Reserved. |
| 7 | Couldn't connect to the app's pipe |

**Environment knobs** (test-oriented; unset in production):

- `ECUIO_SUR_HANDSHAKE_MS` — replaces the 8000 ms handshake window
  (floor 100 ms). The blocked-open test fails fast instead of burning
  the full window.
- `ECUIO_SUR_TEST_FINGERPRINT` — replaces the child's build
  fingerprint, so it stands in for a child from another build and
  refuses every `OP_OPEN`. `MismatchedFingerprintRefusesOpenBeforeVendor`
  uses it.
- `ECUIO_FAKE_CONTROL` — names the fake's control page
  (`tests/fake_control.h`), a named shared-memory page the test process
  creates. Whichever fake instance serves the session reads it on every
  call, the surrogate child's included. A knob set there overrides the
  environment variable of the same name and takes effect mid-session,
  which the child's spawn-time environment can't do. A test also
  queues received messages on it, with any `RxStatus`, and reads what
  the fake publishes there: the process that opened it and its count
  of successful writes. With `ecuio_j2534_force_surrogate_for_testing`
  (`internal.h`), which sends even an x64 DLL to the surrogate,
  `J2534HealthTest` runs each case on both backends against the x64
  fake.
- `ECUIO_FAKE_OPEN_DELAY_MS` — makes the fake's `PassThruOpen` sleep
  before executing (max 60000), simulating a vendor blocked on absent
  hardware. The child inherits the parent's environment, so an x64
  test process arms the x86 child's fake with this knob — the same
  cross-arch consideration that motivates `OP_INJECT`.
- `ECUIO_FAKE_IOCTL_DELAY_MS` — makes the fake's first ioctl after
  load sleep for the given time (max 60000). The
  `TimedOutOpDoesNotDesyncNextRequest` test uses 3500, just past the
  client's 3 s transaction timeout; `UnresponsiveChildFailsFastAfterTwoMissedDeadlines`
  uses 20000, which outlasts both deadlines.
- `ECUIO_FAKE_READ_DELAY_MS` — the same for the fake's first
  `ReadMsgs`: it sleeps first (max 60000), then reads the queue.
  `LateReadReplyIsDroppedAndLogged` uses 1500, past a 50 ms read's
  550 ms transaction timeout.
- `ECUIO_FAKE_DISCONNECT_DELAY_MS` — makes every fake
  `PassThruDisconnect` sleep first (max 60000): a slow vendor teardown.
  Re-read on every call. The bridge's async-disconnect tests use it
  in-proc.
- `ECUIO_FAKE_ZERO_IDS` — `1` makes `PassThruOpen` return device 0 and
  `PassThruConnect` channel 0, read at open.
  `DeviceAndChannelIdZeroAreRealIds` uses it.
- `ECUIO_FAKE_READ_STATUS` — makes every fake `ReadMsgs` return the
  given vendor status with no messages (for example `0x09` for a
  quiet bus, `0x07` for a dead adapter). Re-read on every call, and
  it always zeroes the count. The link-health tests use it (Known
  Issue #11).
- `ECUIO_FAKE_UNTOUCHED_COUNT_STATUS` — makes every fake `ReadMsgs`
  return the given status with the caller's count and message buffer
  left as passed, emulating a vendor that doesn't write its outputs on
  error. `UntouchedCountUnderHardErrorReportsUnhealthy` (both
  backends) and `HardErrorUntouchedCountDeliversNoFrames` (surrogate)
  use it.
- `ECUIO_FAKE_WRITE_STATUS` — makes every fake `WriteMsgs` return
  the given status without recording the message or queuing a
  response, leaving the count as passed: the VX's no-ACK write
  failure. Re-read on every call. `WriteFailureLatchesRequestFailedAndClears`
  and `HardReadFailureOutranksRequestFailed` use it.
- `ECUIO_FAKE_WRITE_ZERO_COUNT` — `1` makes every fake `WriteMsgs`
  return `STATUS_NOERROR` with a count of 0, recording and answering
  nothing: a vendor reporting success for a message it never sent.
  Re-read on every call. `ZeroWrittenCountIsAFailedWrite` uses it.
- `ECUIO_FAKE_SPEC_READ_SEMANTICS` — `1` switches the fake's
  `ReadMsgs` to J2534-1 behavior: up to `NumMsgs` messages, held until
  that many have arrived or the timeout passes; `ERR_TIMEOUT` with a
  short batch when the timeout is nonzero, and `ERR_BUFFER_EMPTY` on
  an empty timeout-0 read. It skips filter gating.
  `SpecTimeoutReadDeliversPartialBatch` uses it.
- `ECUIO_FAKE_VX` — `1` makes the fake behave like the OBDX Pro VX as
  measured ([bench](bench-sessions/2026-10-22.md),
  [vehicle](bench-sessions/2026-10-22-vehicle.md)). Reads batch and
  hold like spec mode, but a short batch comes back `STATUS_NOERROR`
  and any empty read `ERR_BUFFER_EMPTY`. Each accepted write queues a
  TX indication (the 4-byte CAN ID, `RxStatus` `0x09`), and its reply
  arrives 4 ms later, stamped from a 32-bit microsecond clock.
- `ECUIO_FAKE_NO_ACK` — with `ECUIO_FAKE_VX`, a bus with no other
  node: the first three writes after each connect are accepted, with
  an indication and no reply; every later one blocks 500 ms, fails
  `ERR_FAILED` with the count left at 1, and is echoed with `RxStatus`
  `0x201`, as the VX did.
- `ECUIO_FAKE_REPLY_DELAY_MS` — how long after a write its reply
  arrives (default 0, or 4 under `ECUIO_FAKE_VX`). A read sees only
  messages that have arrived.
- `ECUIO_FAKE_OPEN_STATUS`, `ECUIO_FAKE_CONNECT_STATUS`,
  `ECUIO_FAKE_FILTER_STATUS`, `ECUIO_FAKE_VBATT_STATUS`,
  `ECUIO_FAKE_VERSION_STATUS` — make `PassThruOpen`,
  `PassThruConnect`, `PassThruStartMsgFilter`, `READ_VBATT` or
  `PassThruReadVersion` return the given status, and the fake's
  `PassThruGetLastError` describe the refusal. `J2534ConnectTest` uses
  them on both backends.

| 4 | `WRITE` | Single message, 64 bytes max |

| 12 | `READ_VERSION` | `PassThruReadVersion` on the open device: the firmware, DLL and API versions in the reply's three `text` fields. `ERR_NOT_SUPPORTED` when the DLL doesn't export it |

**Data plane.** Reads travel over the pipe as `OP_READ`. The child
asks the vendor for up to `ECUIO_SUR_MAX_FRAMES_PER_READ` (16)
messages with the caller's timeout, skips indications (reading again
with what's left of the timeout when a batch held nothing else),
clamps each payload to 64 bytes (the CAN ID included; Known
Issue #36), and returns the batch with the vendor status. The client caches the batch and hands out one
frame per `read_frame` call, sending a new `OP_READ` only when the
cache is empty. Its transaction timeout is the read timeout plus
500 ms. The response struct is 1608 bytes; a tree built from other
headers is refused at `OP_OPEN` (the build fingerprint above).

Per J2534-1, a read that asks for 16 messages with a nonzero timeout
waits for all 16 and returns `ERR_TIMEOUT` with however many arrived.
The client delivers such a batch and only consults the status when the
batch is empty. Because the child asks for 16 messages, a conforming
vendor also holds each read for the full timeout unless 16 arrive;
with the drain's 20 ms timeout, that costs one or two reads' worth of
each 100 ms cycle. The fake's spec mode
(`ECUIO_FAKE_SPEC_READ_SEMANTICS`) holds a read and returns such a
batch, and `SpecTimeoutReadDeliversPartialBatch` proves it's delivered
after the timeout. The VX holds each read for its full timeout, but returns a
short batch with `STATUS_NOERROR`, not `ERR_TIMEOUT`, and an empty
read with `ERR_BUFFER_EMPTY`; both are handled. Its TX indications
come back in the same reads and are skipped before counting
([bench 2026-10-22](bench-sessions/2026-10-22.md), prep item 6).
On a vehicle its reply batches came with `STATUS_NOERROR` too, and no
read returned `ERR_TIMEOUT`
([vehicle 2026-10-22](bench-sessions/2026-10-22-vehicle.md)).

## Vendor-call relay

Write, ioctl and filter calls behave identically through both
backends ([ADR-0011](adr/0011-vendor-call-relay-wire-forms.md)).

| Call | Rules |
|---|---|
| Ioctl | Whitelisted identically at the seam and in the child: `GET_CONFIG`, `SET_CONFIG`, `READ_VBATT`, `CLEAR_TX_BUFFER`, `CLEAR_RX_BUFFER`, `CLEAR_MSG_FILTERS`. Pointer-bearing IDs are refused. The output gets the first `output_cap` bytes of the result, and the reported length is the whole result's, on both backends. `READ_VBATT` takes the device ID. |
| Version | `PassThruReadVersion` with the device ID; an optional export, like `PassThruGetLastError` |
| Write | Single message; reports the written count |
| Filters | Mask and pattern lengths must match. A flow-control array is required for, and only allowed with, `FLOW_CONTROL_FILTER`. Malformed shapes are refused on the client side, before the pipe. |

The child also re-checks request lengths for `WRITE` (≤64 bytes),
`IOCTL` (≤64 bytes) and `START_FILTER` (≤12 bytes each) before
copying, and answers an oversized request with `ERR_FAILED`. It
answers `ERR_FAILED` as well, without calling the vendor, to an op
that passes the device ID before an `OP_OPEN` has succeeded
(`CONNECT`, `READ_VERSION`, the `READ_VBATT` ioctl), and to one that
passes a channel ID before an `OP_CONNECT` has (`DISCONNECT`, `WRITE`,
the other ioctls, both filter ops). The test-only `OP_INJECT` clamps
its length to 64 bytes.

Vendor statuses come through verbatim. A strict vendor refusing a
second stop surfaces as `ECUIO_ERR_NO_TRANSPORT`.

## Fake vendor DLL

`tests/fake_j2534.cpp` implements the nine mandatory PassThru exports,
plus `PassThruGetLastError` and `PassThruReadVersion`, with SAE
J2534-1 signatures (`__stdcall`, `long` status, 32-bit `unsigned long`
IDs). `fake_j2534.def` exports undecorated names, which x86 needs.
`fake_j2534_legacy` exports the ioctl under its legacy spelling and
has no `PassThruReadVersion`.

| Hook | Purpose |
|---|---|
| `InjectFrame` | Pushes onto a mutex-guarded 16-slot FIFO. By default `ReadMsgs` pops one message per call, whatever `NumMsgs` and the timeout ask for, and returns `STATUS_NOERROR` with zero messages on an empty queue. Spec mode (`ECUIO_FAKE_SPEC_READ_SEMANTICS`) pops up to `NumMsgs` with J2534-1 statuses. The status knobs under [Environment knobs](#surrogate) take precedence over the queue. |
| `GetBufferState`, `GetCurrentHandle` | Observe the FIFO and open/close state |
| `GetLastConnectParams` | Last `PassThruConnect` protocol, baud and flags |
| `GetWriteCount`, `GetRecordedWrite` | Every written message |
| `GetLastFilterStart`, `GetLastFilterStop` | Filter registration shape and stop calls |
| `SetFilterGating` | Makes `ReadMsgs` discard frames that don't match the filter (matching device filter hardware — rejected frames are drained, never parked at the queue head). |
| `GetDisconnectCount` | Monotonic `PassThruDisconnect` count. In-proc observable only — the child's fake instance is a separate process, and no wire op reads it. Through the surrogate, the control page counts the disconnects and closes that name the IDs the fake handed out. |

How the fake behaves:

| Behavior | Detail |
|---|---|
| Write echo | Each write enqueues a response. With a filter active, a 6-byte Mode-01 request gets a canned OBD-II reply, `[rx ID][41][PID][data]`, with values from `g_obd2_canned` (overridable per test); any other write gets `[filter ID BE][payload]` with the first data byte +0x40, so the request's own 4-byte address header is replaced, as a real ECU's reply would be. Without a filter: a raw echo with byte 0 + 0x40. Either way the request→response loop is observable from either architecture. |
| Config table | `SET_CONFIG` / `GET_CONFIG` use a table. Unknown params read back as `0xFFFFFFFF`, standing in for the vendor default. |
| IDs | `PassThruOpen` returns device 1 and `PassThruConnect` channel 0x55, two values a mixed-up caller can't pass by coincidence; `ECUIO_FAKE_ZERO_IDS=1` makes both 0, since J2534 doesn't reserve 0 (`J2534SurrogateTest.DeviceAndChannelIdZeroAreRealIds`) |
| `READ_VBATT` | Returns 13800 mV for the device `PassThruOpen` returned, and fails for any other ID, such as the channel's |
| `PassThruReadVersion` | `fake-fw 1.0`, `fake_j2534 0.3` and `04.04`, for the device `PassThruOpen` returned only |
| Unknown ioctls | Fail |
| Filters | Are tracked. A stopped filter is tombstoned, so stopping it twice fails like a strict vendor would. |
| `ExtraDataIndex` | Equals `DataSize` everywhere (the v04.04 convention) |

Because the fake emits nothing that wasn't injected or echoed, stream
tests assert **exact** counts and payload contents.
