# J2534 transport

How the Windows J2534 Pass-Thru stack works today. Why it is built
this way is covered in ADRs [0007](adr/0007-uri-selected-transports.md)
through [0012](adr/0012-j2534-transport-adoption.md), and
[0014](adr/0014-single-threaded-surrogate.md) for the surrogate's
current shape. For what has
been verified and what hasn't, see [STATUS.md](../STATUS.md) and
[testing.md](testing.md).

**Verification level: HARNESS + BENCH (quiet bus).** Everything below
has been exercised end to end against the in-tree fake vendor DLL,
both same-arch and cross-arch (x64 app → x86 surrogate → x86 fake).
Discovery has also run against real installed drivers (OBDX Pro VT
and VX), and the OBDX Pro VX itself has been loaded and connected
through the surrogate in a formal bench session (2026-10-16, USB
power, no vehicle: vendor open status 0, the 8-byte flow-control
filter shape accepted, clean teardown). An informal 2026-10-20
session confirmed the 4-byte shape that replaced it (logged vendor
status 0) and the fault path on the same adapter
([bench note](bench-sessions/2026-10-20.md)). No vehicle has been
connected.

## URI grammar

```
j2534://[<selector>][?<param>=<value>[&<param>=<value>...]]
```

**Selector:**

| Form | Resolves to |
|---|---|
| *(empty)* | The first discovered device |
| `<vendor-name>` | A discovered device whose name matches, case-insensitively |
| A path ending in `.dll`, or containing `\` or `/` | A direct load. Tests and development use this to reach the fake. |

**Query parameters:**

| Key | Value | Notes |
|---|---|---|
| `baud` | Decimal, nonzero | Default is the ISO 15765 rate of 500 kbit/s. |
| `flags` | `0x`-hex or decimal; 0 allowed | Passed to `PassThruConnect` verbatim. No bit meanings are interpreted yet. |
| `filter` | CAN ID 1–`0x1FFFFFFF` | Receive ID. Registers a `FLOW_CONTROL` filter. |
| `txid` | CAN ID 1–`0x1FFFFFFF` | Transmit ID. Default is the profile's declared transmit ID, else `0x7E0`. |
| `poll` | PID 1–`0xFF` | Single-PID Mode-01 request loop. Replaces the profile's PID rotation: no scheduler is built. Needs a channel, from `?filter=` or the profile's declarations, so `?profile=raw&poll=` alone fails while `?profile=raw&filter=0x7E8&poll=` and a bare `?poll=` under `obd2` work. |
| `profile` | Name, 1–63 chars | ADR-0013 profile override. Validated in `qttune_session_create` before this parser runs; this parser only checks shape. |

Parsing is strict. Each of the following returns `QT_ERR_NO_TRANSPORT`
from `qttune_session_create`, before any DLL is loaded:

- unknown or uppercase keys
- a segment with no `=`
- empty segments, a trailing `&`, or a bare trailing `?`
- non-numeric values, `baud=0`, or out-of-range IDs or PIDs
- `poll` with no channel from either `?filter=` or the profile. This
  check runs at attach rather than in the parser, because it needs the
  profile's declared channels, but attach still runs before the DLL
  loads.

If a key appears twice, the last occurrence wins. A selector that
matches nothing is also `QT_ERR_NO_TRANSPORT`.

**Profile-declared channels (ADR-0013 §4).** When the URI carries no
`?filter=`, the transport derives its channel table from the profile's
signal set at attach — before the device opens — registering one
flow-control filter per channel and routing scheduler requests to the
channel that owns each PID. The `obd2` set declares `0x7E0`
(transmit) / `0x7E8` (receive), so a bare `j2534://` URI starts and
streams with no query parameters.

**Coupling rule.** A request loop, scheduled or `?poll=`, needs at
least one channel to receive on. The check fires at attach, before
any hardware is touched, so it never costs a device open. For
`?poll=` it bites under `raw` without `?filter=`. For the scheduler,
shipped profiles declare channels, so that arm is reachable only by a
future profile author omitting them.

**Example URIs:**

- `j2534://<dll>` — bare: obd2 default, filter on 7E8, requests to 7E0, scheduler active
- `j2534://<dll>?txid=0x7DF` — broadcast requests to 7DF, still filtering 7E8 responses
- `j2534://<dll>?profile=raw&filter=0x7E8&poll=0x0C` — single-PID poll loop, log only. `?filter=` supplies the channel `raw` lacks; without it, create fails.
- `j2534://<dll>?poll=0x0C` — single-PID poll loop under the `obd2` default: only PID 0x0C is requested, on the derived channel, and its signals still decode
- `j2534://<dll>?profile=raw` — no decode, no filter (verbatim passthrough). A real ISO 15765 channel with no filter receives nothing, so add `?filter=` to hear an ECU.
- `j2534://<dll>?profile=obd2` — explicitly selects obd2 with its channel declarations

## Session lifecycle

| Session call | Transport work |
|---|---|
| `qttune_session_create` | Resolve the URI, then derive the channel table and, unless `?poll=` is set, the PID scheduler from the profile's signal set. No hardware is touched yet, and the request-loop-without-channel check fires here. Then `qttune_j2534_open` (load and route the DLL, then PassThruOpen — in surrogate mode, via OP_OPEN after the pipe handshake), then `PassThruConnect` (ISO 15765). Load failures surface here as `QT_ERR_LOAD_FAILED`. |
| `qttune_session_start` | Register one `FLOW_CONTROL` filter per channel — a mid-loop failure unwinds the filters already registered (the channel stays connected until close). Then start the worker. |
| Worker loop | One of three modes, fixed at start. **Scheduler** (a set with muxed defs, such as `obd2`): each 100 ms cycle writes one Mode-01 request for the rotating PID to the channel that owns it, then drains `ReadMsgs` (20 ms timeout, at most 10 reads, the first empty read ends the drain, leftovers carry into the next cycle), then sleeps the remainder against an absolute deadline so drain cost can't drift the cadence. **Poll** (`?poll=`): one request to the channel that owns the PID (channel 0 when no def claims it), one 100 ms read, a 100 ms sleep. `?poll=` outranks the profile, so no scheduler is built. **Passive**: one 100 ms read, a 20 ms sleep. Both request modes keep writing while the link is hard-failed or requests are failing, because each request is the recovery probe; the backoff replaces the normal sleep. |
| `qttune_session_close` | Join the worker → stop every channel's filter (best-effort) → `PassThruDisconnect` → `PassThruClose` → `FreeLibrary`, or the surrogate's shutdown path |

**The teardown order is a hard contract.** The worker calls vendor
functions through pointers, and those pointers dangle the moment the
module unmaps. In surrogate mode the worker is joined before the
client's polite-shutdown and job-kill path runs.

**Receive framing.** ISO 15765 messages carry a 4-byte big-endian address header
in-band.
- *With channels,* the worker checks the 4-byte header against every
  channel's receive ID, strips it on a match, and stamps
  `arbitration_id` with that channel's ID. Non-matching frames are
  dropped but still consume read budget (bounds loop time).
- *Without channels (raw profile),* frames are dispatched verbatim
  with `arbitration_id = 0`.

**Read status.** Both backends map the vendor's `ReadMsgs` result the
same way:

| Vendor result | Transport sees |
|---|---|
| `STATUS_NOERROR`, no messages | No frame |
| `ERR_BUFFER_EMPTY` (0x10), no messages | No frame |
| `ERR_TIMEOUT` (0x09), no messages | `QT_ERR_VEHICLE_TIMEOUT` |
| Any other status, no messages | `QT_ERR_TRANSPORT_HARD_FAILURE` |
| `STATUS_NOERROR` or `ERR_TIMEOUT`, messages returned | The messages are delivered (in-proc one per call, the surrogate as a batch) |
| Any other status, with a nonzero count | The count is ignored, and the row for that status with no messages applies |
| Surrogate: pipe transaction fails, or a response claims more than 16 frames | `QT_ERR_TRANSPORT_HARD_FAILURE` |

Delivering under `ERR_TIMEOUT` is deliberate: a conforming vendor
returns it together with a short batch. Under any other status the
count isn't trusted, because a vendor may leave `pNumMsgs` (and the
buffer) untouched on error. The VX did exactly that on a failed write
("status 7, written 1"). Trusting such a count produces phantom frames
that read as healthy: the surrogate's static read batch would replay
the previous read, and in-proc a zeroed message would dispatch. Both
backends share one rule, `qttune_trusted_count` in `j2534_ptypes.h`.
`ERR_BUFFER_OVERFLOW` (0x12) isn't on its list, so an overflow read
drops its batch and counts as a hard failure.

Messages carrying `TX_INDICATION` or `TX_MSG_TYPE` in `RxStatus`
(transmit-done indications and loopback echoes) are dropped in both
backends. One difference remains: in-proc, a dropped indication
reports "no frame", which ends the drain early (Known Issue #28). The
surrogate drops indications inside the child, so its drain continues.

`START_OF_MESSAGE` (first-frame) indications are not handled yet.

**Link health.** The worker publishes the session's `last_error` and
`error_count` (`qttune_session_get_error_state`). Each read is judged
in this order, first match wins:

1. **Hard read failure**, meaning any status other than `QT_OK` and
   the vehicle-timeout mapping: `QT_ERR_TRANSPORT_HARD_FAILURE` at
   once. The transition counts one episode in `error_count` and starts
   the backoff at 100 ms. This outranks everything below, including a
   failing write.
2. **Latched write failure:** while the last write failed, no other
   read moves the state.
3. **Matched frame** (its header matches a channel and it was
   dispatched, or any frame when there are no channels): `QT_OK`. The
   backoff and the quiet count clear.
4. **Unmatched frame** (delivered, but its header matches no channel):
   the adapter is reading the bus, so a hard failure ends and the
   backoff clears. But the frame isn't a reply to us, so the state
   becomes `QT_ERR_VEHICLE_TIMEOUT`, with no episode. This skips the
   quiet debounce.
5. **Quiet** (an empty `NOERROR` read or `ERR_TIMEOUT`): ten in a row
   (about 1 s in scheduler mode) set `QT_ERR_VEHICLE_TIMEOUT` and
   clear the backoff. A single empty read never does, because every
   drain ends on one.

Writes are judged separately. A failed write latches and, unless a
hard read failure already holds, sets `QT_ERR_REQUEST_FAILED`: one
episode on the transition, backoff from 100 ms. Only a successful
write clears the latch. It returns `QT_ERR_REQUEST_FAILED` to `QT_OK`
without waiting for a reply, because an accepted write proves
requests flow. This is the no-ACK bus (no ECU awake, adapter fine):
reads stay clean while writes fail, so it reads as "requests failing"
rather than an adapter fault.

The backoff doubles after each slept interval, up to 5 s, for as long
as a failure persists. Both request modes keep writing throughout,
because each request is the recovery probe.

In-proc HARNESS tests cover the health machine
(`HardFailureSetsCanonicalErrorAndRecovers`,
`QuietBusDebouncesToVehicleTimeoutWithoutEpisode`,
`UntouchedCountUnderHardErrorReportsUnhealthy`,
`WriteFailureLatchesRequestFailedAndClears`,
`HardReadFailureOutranksRequestFailed`,
`UnmatchedDeliveredFrameGoesQuietNotHealthy`,
`BackoffGrowsUnderSustainedHardFailure`). The bridge polls this state
on its 100 ms coalesce tick, publishes it as `linkState`, and logs
transitions to the Settings activity log. LiveView (banner), the Home
status card and the Settings connection label show it (Known Issue
#11):

| Code | `linkState` | What the user sees |
|---|---|---|
| `QT_OK` | `ok` | No banner; green Home dot and Settings label |
| `QT_ERR_VEHICLE_TIMEOUT` | `quiet` | Amber "Vehicle not responding — quiet bus" |
| `QT_ERR_REQUEST_FAILED` | `requests` | Amber "Requests failing — check the vehicle connection and ignition"; log line "Link: requests failing (N episode(s))" |
| `QT_ERR_TRANSPORT_HARD_FAILURE` | `fault` | Red "Adapter fault — N episode(s), retrying with backoff" |
| Any other code | `degraded` | Red "Link degraded (error N)", forward-compatible |

`QtTuneBridge::linkStateForError` holds the mapping, and
`BridgeTest.LinkStateMapsEveryPublishedCode` pins it.

## Discovery

`qttune_j2534_discover_devices` makes four registry sweeps (two roots
× two WOW64 views) and removes duplicates by DLL path plus vendor
name. Duplicates arise because the views overlap.

- **Roots:**
  - `SOFTWARE\Pass-Thru Support.04.04`, the name the spec uses
  - `SOFTWARE\PassThruSupport.04.04`, without the hyphen, as written
    by real installers (OBDX Pro, under `WOW6432Node` only)
- **Views:** `KEY_WOW64_64KEY` and `KEY_WOW64_32KEY`. These are flags,
  not a hard-coded `WOW6432Node` path, so the sweep works from a
  process of either bitness.
- **Per vendor:** reads `FUNCTIONLIBRARY` (expanding `%VAR%`
  references when the value is `REG_EXPAND_SZ`) and annotates the
  DLL's PE architecture in `reserved[0]`: 1 = x86, 2 = x64, 0 = unknown.

The bridge exposes the result as `discoverJ2534Devices()`, a list of
`{vendorName, dllPath, architecture}` entries for the Settings-page
picker. Each registry entry is treated as one device (Known Issue
#13).

## Loader and routing

`qttune_j2534_open` reads the PE machine field once and picks a
backend ([ADR-0009](adr/0009-pe-architecture-routing.md)):

| Machine type | Backend |
|---|---|
| x86 | Surrogate |
| x64 | In-proc |
| Unknown | In-proc, so the honest load error survives |

Both backends resolve the same nine mandatory exports: `PassThruOpen`,
`Close`, `Connect`, `Disconnect`, `ReadMsgs`, `WriteMsgs`, `Ioctl`,
`StartMsgFilter` and `StopMsgFilter`. A missing export unwinds through
a single failure site, so no `HMODULE` leaks.

These helpers each forward on `is_surrogate`:
- `qttune_j2534_connect_channel` / `disconnect_channel`
- `read_frame` / `write_frame`
- `ioctl`
- `start_msg_filter` / `stop_msg_filter`
- `inject_test_frame` (test only)

`qttune_j2534_backend_name()` reports `"inproc"` or `"surrogate"`.

## Surrogate

[ADR-0008](adr/0008-x86-surrogate-host.md) covers the original design
and [ADR-0014](adr/0014-single-threaded-surrogate.md) its current,
single-threaded shape. This section is the operational detail.

**Spawn.** The client creates the pipe and the job object. It then
launches `qttune-j2534-surrogate.exe <dll> <pipe>` suspended, inside a
`KILL_ON_JOB_CLOSE` job object. **The child connects the pipe
FIRST**, then loads the DLL, resolves its exports, and performs
`PassThruOpen` only when `OP_OPEN` arrives — inside the request loop.
The handshake times out after 8 s (`QTTUNE_SUR_HANDSHAKE_MS`
overrides; test knob).

**Session log.** Each session has one log file holding both halves:
the child's stdout/stderr and the client's own lines.
- **Where:** `%TEMP%\qttune-surrogate.log`, rewritten on every spawn.
  A session that starts while another holds that file gets
  `%TEMP%\qttune-surrogate-<pid>-<n>.log` instead of running without
  a log. `qttune_j2534_sur_log_path()` returns the session's path, and
  the client's first line names it.
- **Stamps:** both sides stamp local wall-clock time
  (`HH:MM:SS.mmm`), so the file reads as one timeline. Each side
  writes whole lines in one call, so lines never splice. Child lines
  start `[surrogate `; client lines start `[sur `.
- **The child logs** each startup stage, and the vendor status of
  every `OPEN`, `CONNECT`, `DISCONNECT`, `IOCTL`, `START_FILTER` and
  `STOP_FILTER`. It logs `OP_WRITE` when its status or written count
  changes, and `OP_READ` when its status changes or frames arrive, so
  expect about 10 lines/s while an ECU answers.
- **Payloads, opt-in:** with `QTTUNE_SUR_LOG_FRAMES=1` in the app's
  environment at launch (the child reads it once, at spawn), the child
  also logs every message it writes and every one the vendor returns,
  before anything is dropped or stripped. The bytes include the 4-byte
  CAN ID, so a reply with 4 data bytes is `len 8`:

  ```
  OP_WRITE frame: status 0, tx 0x00000040, len 6: 00 00 07 E0 01 0C
  OP_READ frame: status 0, rx 0x00000000, ts 4097, len 8: 00 00 07 E8 41 0C 1F 40
  ```

  Indications are logged too, marked "(indication, not delivered)".
  Bytes past 64 are counted (`+N`), not shown. It adds about two lines
  per request cycle. The in-proc backend has no session log, so an x64
  vendor DLL gets no payload capture.
- **The client logs** the spawn first (child pid, DLL, log path),
  written while the child is still suspended. After that it logs only
  trouble:
  - a failed CreateProcess, naming the exe;
  - a handshake timeout;
  - a blocked `OP_OPEN` (no reply, child alive), and the child's
    decoded exit code;
  - a refused `PassThruOpen` or `PassThruConnect`, with the vendor
    status;
  - transaction failures and desyncs;
  - a skewed reply (`num_frames` or ioctl `data_len` past the wire
    limit);
  - frames dropped with a late `OP_READ` reply (below).
- **stderr:** the client also writes its lines to the app's stderr,
  but a GUI launch no longer needs a redirect to keep them.

**Late replies.** When a transaction times out, the client remembers
its request ID. Before the next request, it reads and discards that
late reply, so the next request isn't paired with it. If the late
reply was an `OP_READ`'s, its frames are dropped with it, and the
client logs `drain_pending: dropped N frame(s)`. Getting there takes a
read the child answers more than 500 ms past its own timeout.

This ordering makes the wire itself the diagnostic:

- Handshake times out, child alive → the child never opened the
  pipe; process startup stalled before any vendor code ran.
- Pipe connected → the child started. It hasn't loaded the DLL yet.
- Child exits before answering `OP_OPEN` → its exit code names the
  stage: 4 (the DLL didn't load) or 5 (an export is missing).
- `OP_OPEN` answered → the DLL loaded, all nine exports resolved, and
  `PassThruOpen` returned: a device ID, or a refusal with the vendor
  status. After a refusal the client shuts the child down.
- `OP_OPEN` unanswered, child alive → the vendor is blocked in
  `DllMain` or `PassThruOpen`, typically waiting for absent hardware.
  `OP_OPEN` gets its own handshake window. On timeout the client
  terminates the child, because a single-threaded child stuck in
  vendor code can't answer `OP_SHUTDOWN`. Only a reply that *timed
  out* counts as blocked. A broken pipe means the child is exiting
  with code 4 or 5, so the client waits for the exit and decodes it.
  Before 2026-10-20 it checked only whether the child was alive, and
  that check could run in the moment between the pipe closing and the
  process ending. A DLL that failed to load was then logged as a
  blocked vendor.
- A failed handshake cancels the pending `ConnectNamedPipe` before the
  client releases its event and pipe.

Before 2026-10-16, `PassThruOpen` ran before the pipe connect, so a
blocked vendor open was indistinguishable from any other pre-pipe
stall and cost the full timeout with no stage information.

**One thread, one request at a time** ([ADR-0014](adr/0014-single-threaded-surrogate.md)).
The child reads a request, makes at most one vendor call, writes the
response and loops, so vendor calls are serialized by construction
and no lock exists. The vendor status in each response is data: a
refused ioctl, a failed filter stop or an empty read is answered and
the loop continues. Only `OP_SHUTDOWN` or a broken pipe ends it,
after which the child disconnects any open channel, closes the
device and unloads the DLL. A successful `OP_DISCONNECT` clears the
channel, so teardown never disconnects twice. Whether a device and a
channel are open is tracked with explicit flags, not by treating ID 0
as "none": J2534 doesn't reserve 0. A vendor call that never
returns leaves the child hung; the client's transaction times out,
and the kill-on-close job reaps the child at close.

**Child exit codes.** These are the first thing to check when a spawn
fails. The client decodes the code into the session log
(`open: child exited with code N (...)`). On exit 5 the child's lines
names every missing export, so the log alone identifies the gap;
`dumpbin /exports` remains the cross-check for x86 name decoration.

| Code | Stage that failed |
|---|---|
| 1 | Argument count |
| 2 | Retired (attached the shared ring before ADR-0014). Not reused. |
| 3 | Retired (mapped the ring view and event before ADR-0014). Not reused. |
| 4 | `LoadLibrary` of the vendor DLL |
| 5 | A mandatory export is missing (on x86, check export name decoration) |
| 6 | Reserved. |
| 7 | Couldn't connect to the app's pipe |

**Environment knobs** (test-oriented; unset in production):

- `QTTUNE_SUR_HANDSHAKE_MS` — replaces the 8000 ms handshake window
  (floor 100 ms). The blocked-open test fails fast instead of burning
  the full window.
- `QTTUNE_FAKE_OPEN_DELAY_MS` — makes the fake's `PassThruOpen` sleep
  before executing (max 60000), simulating a vendor blocked on absent
  hardware. The child inherits the parent's environment, so an x64
  test process arms the x86 child's fake with this knob — the same
  cross-arch consideration that motivates `OP_INJECT`.
- `QTTUNE_FAKE_IOCTL_DELAY_MS` — makes the fake's first ioctl after
  load sleep for the given time (max 60000). The
  `TimedOutOpDoesNotDesyncNextRequest` test uses 3500, just past the
  client's 3 s transaction timeout.
- `QTTUNE_FAKE_READ_STATUS` — makes every fake `ReadMsgs` return the
  given vendor status with no messages (for example `0x09` for a
  quiet bus, `0x07` for a dead adapter). Re-read on every call, and
  it always zeroes the count. The link-health tests use it (Known
  Issue #11).
- `QTTUNE_FAKE_UNTOUCHED_COUNT_STATUS` — makes every fake `ReadMsgs`
  return the given status with the caller's count and message buffer
  left as passed, emulating a vendor that doesn't write its outputs on
  error. `UntouchedCountUnderHardErrorReportsUnhealthy` (in-proc) and
  `HardErrorUntouchedCountDeliversNoFrames` (surrogate) use it.
- `QTTUNE_FAKE_WRITE_STATUS` — makes every fake `WriteMsgs` return
  the given status without recording the message or queuing a
  response, leaving the count as passed: the VX's no-ACK write
  failure. Re-read on every call. `WriteFailureLatchesRequestFailedAndClears`
  and `HardReadFailureOutranksRequestFailed` use it.
- `QTTUNE_FAKE_SPEC_READ_SEMANTICS` — `1` switches the fake's
  `ReadMsgs` to J2534-1 behavior: up to `NumMsgs` messages,
  `ERR_TIMEOUT` with a short batch when the timeout is nonzero, and
  `ERR_BUFFER_EMPTY` on an empty timeout-0 read. It returns at once
  rather than waiting out the timeout, and skips filter gating.
  `SpecTimeoutReadDeliversPartialBatch` uses it.

**Wire ops** (`surrogate_protocol.h`, append-only):

| # | Op | Notes |
|---|---|---|
| 1 | `OPEN` | `PassThruOpen`. The child loads the DLL after the pipe connect, before it serves this first request. |
| 2 | `CONNECT` | `PassThruConnect` |
| 3 | `IOCTL` | Flattened `SCONFIG` pairs; whitelisted |
| 4 | `WRITE` | Single message, 64 bytes max |
| 5 | `READ` | Batched `ReadMsgs`, up to 16 messages, with the caller's timeout. Returns the frames and the vendor status. |
| 6 | `SHUTDOWN` | |
| 7 | `DISCONNECT` | |
| 8 | `INJECT` | Test only; forwarded to the fake's `InjectFrame` |
| 9 | `START_FILTER` | Flat mask, pattern and flow-control arrays, 1–12 bytes |
| 10 | `STOP_FILTER` | |

**Data plane.** Reads travel over the pipe as `OP_READ`. The child
asks the vendor for up to `QTTUNE_SUR_MAX_FRAMES_PER_READ` (16)
messages with the caller's timeout, drops indications and loopback
echoes, clamps each payload to 64 bytes, and returns the batch with
the vendor status. The client caches the batch and hands out one
frame per `read_frame` call, sending a new `OP_READ` only when the
cache is empty. Its transaction timeout is the read timeout plus
500 ms. The response struct is 1368 bytes, so rebuild both trees
after any change to it (Known Issue #19).

Per J2534-1, a read that asks for 16 messages with a nonzero timeout
waits for all 16 and returns `ERR_TIMEOUT` with however many arrived.
The client delivers such a batch and only consults the status when the
batch is empty. Because the child asks for 16 messages, a conforming
vendor also holds each read for the full timeout unless 16 arrive;
with the drain's 20 ms timeout, that costs one or two reads' worth of
each 100 ms cycle. The fake's spec mode
(`QTTUNE_FAKE_SPEC_READ_SEMANTICS`) returns such a batch, and
`SpecTimeoutReadDeliversPartialBatch` proves it's delivered; spec mode
doesn't hold the read for the timeout, so the time cost isn't
modelled. The VX answers a truly empty read with `STATUS_NOERROR` and
no messages (2026-10-20, prep item 6), which maps to "no frame".
Whether it ever pairs `ERR_TIMEOUT` with data is a talking-bus
question.

## Vendor-call relay

Write, ioctl and filter calls behave identically through both
backends ([ADR-0011](adr/0011-vendor-call-relay-wire-forms.md)).

| Call | Rules |
|---|---|
| Ioctl | Whitelisted identically at the seam and in the child: `GET_CONFIG`, `SET_CONFIG`, `READ_VBATT`, `CLEAR_TX_BUFFER`, `CLEAR_RX_BUFFER`, `CLEAR_MSG_FILTERS`. Pointer-bearing IDs are refused. |
| Write | Single message; reports the written count |
| Filters | Mask and pattern lengths must match. A flow-control array is required for, and only allowed with, `FLOW_CONTROL_FILTER`. Malformed shapes are refused on the client side, before the pipe. |

The child also re-checks request lengths for `WRITE` (≤64 bytes),
`IOCTL` (≤64 bytes) and `START_FILTER` (≤12 bytes each) before
copying, and answers an oversized request with `ERR_FAILED`.

Vendor statuses come through verbatim. A strict vendor refusing a
second stop surfaces as `QT_ERR_NO_TRANSPORT`.

## Fake vendor DLL

`tests/fake_j2534.cpp` implements the nine PassThru exports with SAE
J2534-1 signatures (`__stdcall`, `long` status, 32-bit `unsigned long`
IDs). `fake_j2534.def` exports undecorated names, which x86 needs.

| Hook | Purpose |
|---|---|
| `InjectFrame` | Pushes onto a mutex-guarded 16-slot FIFO. By default `ReadMsgs` pops one message per call, whatever `NumMsgs` and the timeout ask for, and returns `STATUS_NOERROR` with zero messages on an empty queue. Spec mode (`QTTUNE_FAKE_SPEC_READ_SEMANTICS`) pops up to `NumMsgs` with J2534-1 statuses. The status knobs under [Environment knobs](#surrogate) take precedence over the queue. |
| `GetBufferState`, `GetCurrentHandle` | Observe the FIFO and open/close state |
| `GetLastConnectParams` | Last `PassThruConnect` protocol, baud and flags |
| `GetWriteCount`, `GetRecordedWrite` | Every written message |
| `GetLastFilterStart`, `GetLastFilterStop` | Filter registration shape and stop calls |
| `SetFilterGating` | Makes `ReadMsgs` discard frames that don't match the filter (matching device filter hardware — rejected frames are drained, never parked at the queue head). |
| `GetDisconnectCount` | Monotonic `PassThruDisconnect` count. In-proc observable only — the child's fake instance is a separate process. The wire query op once planned for a cross-process read was never built (formerly Known Issue #23). A surrogate test could instead count the child's `OP_DISCONNECT` lines in the session log (`qttune_j2534_sur_log_path()`), but none does yet. |

How the fake behaves:

| Behavior | Detail |
|---|---|
| Write echo | Each write enqueues a response. With a filter active, a 6-byte Mode-01 request gets a canned OBD-II reply, `[rx ID][41][PID][data]`, with values from `g_obd2_canned` (overridable per test); any other write gets `[filter ID BE][payload]` with the first data byte +0x40, so the request's own 4-byte address header is replaced, as a real ECU's reply would be. Without a filter: a raw echo with byte 0 + 0x40. Either way the request→response loop is observable from either architecture. |
| Config table | `SET_CONFIG` / `GET_CONFIG` use a table. Unknown params read back as `0xFFFFFFFF`, standing in for the vendor default. |
| `READ_VBATT` | Returns 13800 mV |
| Unknown ioctls | Fail |
| Filters | Are tracked. A stopped filter is tombstoned, so stopping it twice fails like a strict vendor would. |
| `ExtraDataIndex` | Equals `DataSize` everywhere (the v04.04 convention) |

Because the fake emits nothing that wasn't injected or echoed, stream
tests assert **exact** counts and payload contents.
