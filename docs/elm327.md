# ELM327 transport

How `elm327://` drives an ELM327-compatible adapter: an OBDLink's STN
chip, the OBDX in its ELM mode, or a clone. Why it is built this way is
in [ADR-0026](adr/0026-elm327-transport.md) and its dated appendices,
with [ADR-0028](adr/0028-app-fed-streams.md) for Bluetooth through the
app and [ADR-0015](adr/0015-request-engine.md) for the requests, which
J2534 shares. For what has been verified and what hasn't, see
[STATUS.md](../STATUS.md) and [testing.md](testing.md).

**Verification level: HARNESS, BENCH, one vehicle, one phone.**
- **HARNESS:** everything below runs against the in-tree fake ELM327
  (`tests/fake_elm327.h`) behind the port opener, a loopback TCP
  socket and an app stream on every platform, and over a
  pseudo-terminal through the OS's serial code on Linux and macOS.
- **BENCH:** the OBDX Pro VX on USB and over its WiFi, with no bus
  ([2026-10-27-elm327-bench](bench-sessions/2026-10-27-elm327-bench.md)
  and its `-2` to `-6` sheets).
- **Vehicle:** one car, read-only, through the OBDLink MX+ over
  Bluetooth and the VX in ELM mode over USB
  ([2026-10-27-elm327-vehicle](bench-sessions/2026-10-27-elm327-vehicle.md)),
  and through the MX+ from an Android phone, in the background and with
  the screen off
  ([2026-10-28-android-8](bench-sessions/2026-10-28-android-8.md),
  [2026-10-28-android-11](bench-sessions/2026-10-28-android-11.md),
  [2026-10-29-android](bench-sessions/2026-10-29-android.md)).
- [bench-prep.md](bench-sessions/bench-prep.md), items 11 to 25, holds
  each hardware assumption and its evidence.

## Layers

| File | What it does |
|---|---|
| `core/src/elm327_protocol.h` | The wire, pure: bytes into lines and line kinds, frame lines by addressing mode, ISO-TP reassembly per CAN ID, the values (`AT RV`, `STVR`, `AT PPS`), the commands it formats, and which PIDs get the response-count digit. No I/O, no clock, no allocation |
| `core/src/elm327_transport.cpp` | The session: the URI, the setup, the worker, link health, passive listening |
| `core/src/elm327_port.cpp` | A serial port: `\\.\COMn` on Windows, `termios` elsewhere |
| `core/src/elm327_tcp.cpp` | A WiFi adapter's TCP socket |
| `core/src/elm327_stream.cpp` | An app-fed stream (`ecuio/stream.h`): a link only the app's framework reaches, Bluetooth on Android |
| `core/src/elm327_log.cpp` | The wire log |
| `core/src/serial_ports.cpp` | Discovery: `ecuio_serial_ports` (`ecuio/serial.h`) |
| `core/src/request_setup.h`, `request_engine.h`, `link_health.h` | Shared with J2534: the channels and requests from the profile, the engine, the link's state |

Every port is an `ecuio_elm327_port_ops_t` (`internal.h`: write, read
with a timeout, close), so the setup and the worker never know which
kind they run on. Tests replace the opener with
`ecuio_elm327_set_port_opener`.

## URI grammar

```
elm327://<port>[?profile=…][&did=…][&baud=500000|250000][&serial=300..4000000]
               [&filter=…][&txid=…][&poll=…][&probe=0|1][&identify=0|1]
```

The text before the query is the port, one of:

| Form | Example | Opens |
|---|---|---|
| A serial port | `COM7` (`COM1`–`COM255`), `/dev/ttyUSB0`, `/dev/cu.OBDLinkMX` | The OS's serial port, at 38400 bit/s unless `?serial=` says otherwise |
| A TCP address | `192.168.4.1:23`, `192.168.0.10:35000` | A socket: four decimal octets, a colon and a port 1–65535; no host names, no IPv6, no leading zeros |
| An app stream | `bt:00:11:22:33:44:55`, `ble:…` | The stream the app registered under that name, matched whole |

- `baud` is the CAN rate, which picks the protocol: `AT SP 6` (11-bit,
  500 kbit/s), `7` (29-bit, 500), `8` (11-bit, 250) or `9` (29-bit,
  250).
- `serial` is a serial port's rate; with a TCP address or a stream it
  is `BAD_URI`, since a socket has none.
- `profile`, `did`, `filter`, `txid`, `poll`, `probe` and `identify`
  mean what they mean for `j2534://` ([j2534.md](j2534.md#uri-grammar));
  the default profile is `obd2`.
- The channels come from the profile, or `?filter=`/`?txid=`. They
  must all be 11-bit or all 29-bit (`AT SP` takes one mode), or the
  URI is `BAD_URI`.
- A session with nothing to ask and no channel is `NOT_IMPLEMENTED`:
  listening to the whole bus unfiltered is a later step.

Every refusal happens at create, before the port opens, with a detail
naming the fix.

## The setup

At attach, after the port opens, and again after any reset or reopen.
Each command waits for its prompt before the next is sent.

1. **The reset.** `AT Z` must answer an `ELM327` version. An adapter
   that answers `OK` alone (the VX) is asked `AT I`, which must. The
   reset is sent twice at most: an adapter left monitoring takes the
   first byte as its stop.
2. **The contract**, each answered `OK` or the connect is refused:

   | Command | Why |
   |---|---|
   | `AT E0`, `AT L0`, `AT S0` | No echo, linefeeds or spaces: fewer bytes |
   | `AT H1` | The CAN ID and the PCI byte on every line |
   | `AT D0` | No length digit after the ID |
   | `AT CAF1`, `AT CFC1` | The adapter adds the PCI bytes when sending and sends the flow control after a First Frame |
   | `AT SP <6-9>` | ISO 15765-4 at the mode and rate, never a search |
   | `AT AT1` | Adaptive timing |
   | `AT ST 19` | The first reply's timeout: 25 × 4 ms, the engine's 100 ms wait |
   | `AT SH`, plus `AT CP` for 29-bit | The first channel's request ID |
   | `AT CRA <id>`, or `AT CF`/`AT CM` | A receive filter passing exactly the channels' reply IDs |

   A command whose answer holds a reset banner and no `OK` (a reset
   still finishing when it went out: the MX+ over a new Bluetooth link
   answers `AT Z` twice) is sent once more, with a wire-log line.
3. **The readings**, which never fail a connect: `AT I`, then on an
   STN `STI` and `STVR`, otherwise `AT RV`, and on an STN `AT PPS`
   for parameter 2A. Each goes into the session info; `?` or an odd
   answer means "not present".

A refusal reads "the adapter on COM7 answered ATH1 with '?', not OK"
(`VENDOR_REFUSED`), or "didn't answer ATZ within 5 s"; a port that
fails reads "COM7: …" (`LOAD_FAILED`).

The adapter is never sent anything that writes its memory, a serial
number request (`STSN`), the OBDX's `DX` commands or an STN's `STMA`.

## The worker

One thread per session, with **one command outstanding for the whole
adapter**: an ELM327 takes the next command only after its prompt.
Each pass:

1. Expires the engine's waits; a timeout is counted toward "quiet".
2. Asks the first channel in turn with a request due. It sends `AT SH`
   only when the channel changes, then the request as hex. The
   response-count digit `1` goes after a Service 01 request to a
   physical ID whose PID is a supported-PID bitmap or has every def
   ending within a Single Frame (`elm327_one_frame_pids_for`); a reply
   that turns out to span frames takes the PID off the digit for the
   session (ADR-0026's appendix of 2026-10-29). Service 09, 0x22 and a
   functional ID never get it.
3. Reads to the prompt. Echo lines are skipped; 5 s with no line and no
   prompt is silence, a hard failure.
4. With nothing due, reads what comes unasked for up to 100 ms (10 ms
   slices while a request is due soon).

Before every command, `drain` reads what arrived unasked: a reset
banner re-runs the setup, a stray prompt is dropped.

Frames carry the host's time: an ELM327 line has no timestamp. Each
reassembled message goes to the session's callbacks (with
`ECUIO_FRAME_FLAG_EXTENDED` for 29-bit) and, when it answers a
request, to the engine.

### Line kinds and the link

| The adapter says | The link |
|---|---|
| A frame line on a channel's reply ID | A message: `ok` |
| `NO DATA` | Nothing; the engine's wait judges the request, so a silent ECU and no bus both read as quiet |
| `CAN ERROR`, `BUS ERROR`, `BUS BUSY`, `FB ERROR`, `UNABLE TO CONNECT`, `ERRxx`, or `?` to a request | The request never reached the bus: a failed write, "Requests failing" |
| `BUFFER FULL` | Frames were lost: the next frame carries `ECUIO_FRAME_FLAG_OVERFLOW`; the link is unchanged |
| A reset (`LV RESET`, or a version banner) | The setup runs again; a hard failure only if it fails |
| The port failing, or 5 s of silence | A hard failure: the port closes and reopens on the backoff (100 ms, doubling to 5 s), and the setup runs again |

The link states and episodes follow `link_health.h`, as J2534's do
([j2534.md](j2534.md#session-lifecycle)): the probe and identification
re-run after a recovery.

### ISO-TP

With `AT H1` and `AT CAF1` the adapter prints every CAN frame with its
PCI byte, and core reassembles: a Single Frame whole, a First Frame and
its Consecutive Frames per CAN ID (eight messages under way at once),
up to ISO 15765-2's 4,095 bytes. A gap, a repeat, a short frame or the
reply's end drops the message under way; a frame no message can use is
counted malformed. Two ECUs' replies can interleave.

## Passive listening

A session that asks nothing (`?profile=raw`, which hears the engine
ECU's channel, or a registered set with channels and no requests)
monitors with `AT MA` instead
(ADR-0026's appendix "passive listening"):

- `AT MA` keeps the setup's receive filter, so it hears the channels'
  IDs only; `STMA` would open the hardware filter, so it is never sent.
- A monitor never acknowledges a frame, so it can't disturb the bus.
- 5 s with no line: one space stops it, and its prompt within 5 s
  restarts it at once; no prompt is silence, a hard failure.
- It ends with a prompt on its own (a plain ELM327's `BUFFER FULL`
  does): after `BUFFER FULL` it restarts at once, otherwise after a
  backoff from 100 ms to 5 s.
- At close, one space stops it, waiting at most 1 s for the prompt.
  Never a CR, which repeats the last command.

## Reading a session

- **The "Session:" line** names the firmware (`AT I`, plus `STI` on
  an STN), the CAN rate, the channels and the battery from `STVR` or
  `AT RV`. It warns when an STN's parameter 2A has bit 2 clear, which
  means a `7F xx 78`'s answer is lost.
- **The wire log**, `ecuio-elm327.<YYYYMMDD-HHMMSS-mmm>.log` in the
  temporary directory (`%TEMP%`, `TMPDIR`; the app's cache on
  Android), the newest 50 kept. It always records the URI, the port
  and its rate, every setup command and its answer, the readings, lines
  that came unasked, and the port's failures, reopens and resets. With
  `ECUIO_SUR_LOG_FRAMES=1`, which a recording sets, it also records
  every request and reply line, each prompt with its time after the
  command. The identification replies are in it as hex (`49 02` is the
  VIN): scrub before sharing
  ([CONTRIBUTING.md](../CONTRIBUTING.md#handling-vehicle-data)).

## App-fed streams

A link only the app's framework can open, classic Bluetooth on Android
or Bluetooth LE, reaches core as a stream
([ADR-0028](adr/0028-app-fed-streams.md), `ecuio/stream.h`):

- The app registers a stream by name (`bt:<address>`) with three
  callbacks, `open`, `write` and `close`, each returning at once.
- It pushes what happens: `opened`, `failed` with a reason, and the
  bytes it received.
- Core waits up to 10 s for an open on its own thread, keeps a 64 KB
  buffer (bytes past it fail the link, since text can't be
  resynchronized mid-reply), and reopens on the worker's backoff, so
  the app never reconnects by itself.
- Callbacks never run under a core lock, and a push never calls back.

On Android the app's side is `app/btstream.cpp` (an SPP socket for a
classic adapter, the GATT service it picks for a BLE one) and the
`Bluetooth` QML singleton. On a desktop, a paired classic adapter is a
serial port, so no stream is needed.

## The adapters on hand

| Adapter | Link | What to know |
|---|---|---|
| **OBDX Pro VX**, ELM mode | USB (an STMicroelectronics virtual COM port), WiFi at `192.168.4.1:23` | `AT Z` answers `OK` alone, `AT I` gives `ELM327 V2.1`. With no bus every request answers `NO DATA`, so the bench reads quiet. Its WiFi is an open access point; after a client leaves with its socket open, its network side stops answering until a power cycle; a session on its USB port shuts WiFi out. One link at a time |
| **OBDLink MX+** (STN2255) | Classic Bluetooth SPP | Powered only from the OBD connector, so it runs only on a car. Over a new Bluetooth link it can answer `AT Z` twice, the second time late, which the setup's resend handles. Parameter 2A at its default waits past a `7F xx 78` |

Other adapters and clones are untested.

## The fake ELM327

`tests/fake_elm327.h`, header-only and allocation-free, is the HARNESS
tier's adapter. It keeps the settings the setup sends and honors them
in what it prints, answers requests from the same ECU as the fake J2534
DLL (`tests/fake_ecu.h`), prints at most the response-count digit's
number of frame lines, and monitors under `AT MA`. Knobs reproduce
what the bench found: `reset_ok` (the VX's reset), `stale_banner` (the
MX+'s late reset), `no_data`, `can_error`, `pending`, `dropped`, `hung`,
`full_ends_monitor` and more; the list is in the header.

## Troubleshooting

| What you see | Likely cause |
|---|---|
| "COM7: no such port" | The adapter isn't plugged in or paired, or Windows gave it another number: Settings lists the ports it knows |
| "didn't answer ATZ within 5 s" | Nothing ELM327-like on that port, the wrong serial rate (`?serial=`), or another program holds the port |
| "answered ATSP6 with '?', not OK" | Not an ELM327 that speaks CAN, or a clone missing a command the contract needs |
| "no answer within 2 s (is this computer on the adapter's WiFi?)" | The computer isn't on the adapter's network, or the adapter's WiFi has hung: power-cycle it |
| "the connection was cut off on this computer's side" | The computer left the adapter's WiFi |
| "Requests failing" | `CAN ERROR` and kin: the adapter reaches no CAN bus (ignition off, a non-CAN car, the wrong rate) |
| Quiet, no values | `NO DATA` to everything: the ECU doesn't answer that ID, or there's no bus (the VX on the bench) |
| "Adapter fault" that won't clear | The port keeps failing: the cable, Bluetooth, or a WiFi adapter that needs a power cycle |
