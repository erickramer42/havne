# BENCH — laptop quiet-bus run 2026-10-25 (VX, USB power, no vehicle)

**Time:** 15:55–16:15 local, the desk check before the
[vehicle session](2026-10-25-vehicle.md) the same afternoon.
**Machine:** the laptop that goes to the car, a second machine with
the VX driver installed, built from source with both trees fresh, at
`4b21178`; Avast antivirus running.
**Adapter:** OBDX Pro VX through the x86 surrogate, on USB power only.
**Run sheet:** [bench-runsheet.md](bench-runsheet.md).
**Evidence:** every connect's session log from 16:02 on, the account
name and local paths replaced, in [2026-10-25-bench/](2026-10-25-bench/).
**Record sessions** was on from 16:05: each of those connects' logs
reads "frame logging on", and each wrote a recording (kept on the
laptop).

**Result: every phase behaved as on the 2026-10-22 bench run**
([2026-10-22](2026-10-22.md)), on a machine that hadn't run the VX
before. Two things the run sheet doesn't describe appeared, because
it predates the PID-support probe and vehicle identification: the
first writes are now `01 00`, `01 04` and `09 02`, and the activity
log adds an ECU line. One cross-arch test failed once, and the app
closed and reopened itself once after the first mock connect; both
point at the antivirus, neither is confirmed.

## Observations

1. **Pre-flight, `scripts/verify.sh`:** the cross-arch step ran 73 of
   74 cases green. `J2534SurrogateTest.OpenConnectInjectReadCloseCycle`
   failed after 27 s: its first transaction, `OP_OPEN`, ended in
   `ov_read failed … err=109` (`ERROR_BROKEN_PIPE`), so the surrogate
   exited before it answered. It passes on rerun about half the time
   on this laptop, with Avast running. Antivirus holding or stopping a
   newly built exe is the run sheet's suspect for a startup stall;
   here the child died instead. Unconfirmed: no exclusion was tried.
2. **The app closed and reopened by itself** a few seconds after the
   first `mock://demo` connect, and came back disconnected. No session
   log covers it (the mock spawns no surrogate) and no crash was
   captured. A suspect, unconfirmed: antivirus that runs an unknown
   program in a sandbox, then relaunches it. Windows' Application log
   would show a crash of `qttune.exe` if it was one.
3. **The absent VX** refuses `PassThruOpen` with status 34, and its
   `PassThruGetLastError` text reads "Error reporting not yet added",
   as on the dev machine.
4. **Phase 1, the bare URI.** The first three writes succeed (`01 00`,
   the probe's first bitmap; `01 04`, the rotation; `09 02`,
   identification), and the fourth and every later one blocks about
   0.5 s and returns status 7. The probe's bitmap goes unanswered, so
   the activity log reads "ECU 0x7E8: no answer to the supported-PID
   query; 10 requests, none dropped" at +0.24 s, then "Link: requests
   failing (1 episode(s))" at +0.9 s. The gaps between writes grow
   0.6, 0.7, 0.8, 1.0, 1.4, 2.2, 3.8 s, and settle at 5.6 s by the
   80 s connect: the backoff at its cap. Both processes stayed under
   1 % CPU.
5. **Phase 2, listen only.** No writes, every read
   `ERR_BUFFER_EMPTY` (16), amber "Vehicle not responding" at +1.2 s,
   no frames.
6. **Phase 3.** Each URI connects and goes to "Requests failing" as
   Phase 1 does. With writes failing, `?poll=` is paced by the same
   backoff (3 writes ok, then 0.6 s growing to 5.6 s), not the
   run sheet's 220 ms, which holds only while writes succeed. Each
   connect wrote a recording folder (`events.log` with the URI, "surrogate
   frame logging on" and the transition; `frames.csv` and
   `signals.csv` header only) and kept its session log by its last
   line's stamp.
7. **Phase 4, VBATT.** "battery 0.0 V" on every connect: on USB power
   there is no vehicle battery at the connector, so the VX reads none.
8. **The adapter's versions,** from every "Session:" line: firmware
   `FW:1.0.1.0 HW:1.0.0.0`, DLL `1.8.9586.12845`, API `04.04`.
9. **A URI typed with leading spaces** fails as no transport: core
   matches the scheme at the first character, and Settings passes the
   field as typed.
10. **The run sheets and the build.** Read top to bottom,
    development.md's "Build configurations" gives the app's commands
    first and the Win32 tree's later, and explains
    `QTTUNE_SURROGATE_SOURCE` (the app build's setting) before either
    tree is built; the run sheets say "fresh build, Win32 first"
    without pointing at the commands.
