## Findings

1. **The full `obd2` set runs on the car through the MX+.** The probe
   kept the 43 PIDs the bitmaps list and dropped the 49 others on the
   bitmaps alone; Live hid the 81 signals of the dropped PIDs.
2. **The rate classes refresh near their estimates:** fast 0.87 s, slow
   3.53 s, at 26.0 requests a second.
3. **PIDs 23 and 59 read one sensor** on the test car: the same value
   in both. ADR-0039 §3 moves a duplicate to the slow class.
4. **PIDs 55 and 56 answer one byte** where the set defines two fields
   each, so their bank 3 rows never fill and aren't hidden.
5. **The trouble-code read works on a real ECU** with no codes stored:
   every list answered empty, readiness read as J1979 says for a spark
   engine, the freeze-frame bitmap answered and PID 02 said none was
   stored; Read again repeated it. The VX's report the same morning is
   the same ([2026-10-31-vehicle](2026-10-31-vehicle.md)).
6. **Live plots all 49 signals by default,** which makes the strip
   chart unreadable ([live-idle.jpg](2026-10-31-elm327-vehicle/live-idle.jpg)).
7. No stall: the VX session's note of data stopping didn't recur here.

## Consequences

- One of PIDs 23 and 59 moves to the slow class (ADR-0039 §3).
- Live either hides a field its PID's reply is too short for, or the
  set drops the bank 3 trims (55 and 56's B), which no common engine
  has.
- A connect plotting every signal needs a smaller default.
