## Purpose

`elm327://` on a real adapter for the first time, and the Win32 serial
port code's first run (it has no automated test). Goals, in order:

1. The VX gets a serial port over USB (BENCH prep #11)
2. It takes the setup's every command (#12) and gives its readings
   (#13)
3. With no bus at all, its `NO DATA` reads as quiet (#15), and an
   unplugged cable as a fault that recovers (#16)

The evidence is each connect's wire log,
`%TEMP%\ecuio-elm327.<YYYYMMDD-HHMMSS-mmm>.log`: every command, every
line the adapter sent back, and, with **Record sessions** on, every
request and reply with its prompt's time after the request. The
activity log (`events.log` when recording) has the link's states.

## If it fails, suspect

| Symptom | Suspect |
|---|---|
| "COMn: the port is in use by another program" | The vendor app, or a `j2534://` session, holds it |
| "the adapter on COMn didn't answer ATZ within 5 s" | The serial rate: retry with `?serial=115200`. Then a port that isn't the VX's |
| "answered ATZ with '…', not an ELM327 version", or ATI | Garbled text: the serial rate, as above. Readable text: the adapter isn't in ELM mode, or another device is on the port |
| Connects, then red "Adapter fault" with the cable in | The port's reads or writes failing: copy the activity log whole |
| The app crashes | Capture the activity log and stop |

## Findings

1. **The setup goes through.** `AT Z` answered `OK` alone, `AT I`
   `ELM327 V2.1`, and every contract command `OK`, each prompt within
   0.3 ms; `AT RV` `0.00V` in 14.4 ms. The "Session:" line read
   "ELM327 adapter (ELM327 V2.1); …; battery 0.0 V", connected 127 ms
   after Connect was pressed. The first connect's `AT Z` came back with
   no echo: the VX kept the earlier probe's `AT E0` across port opens
   (its USB power never dropped), and `AT Z` turned it back on.
2. **No bus is quiet.** Every request answered `NO DATA` (325 in the
   first connect's 97 s). The first three after each setup came 100 ms
   after the request, `AT ST 19`'s timeout; every later one 300 ms. With
   no node to acknowledge them, the VX's CAN controller holds three
   frames, and each later request waits for room before its 100 ms
   starts: the J2534 path's three writes accepted, then each blocking
   (BENCH prep #8). The link went quiet 2.4 s after the connect, with no
   episode; the probe found no supported-PID bitmap, and identification
   ended "13 unanswered".
3. **The cable pull recovers.** The read failed at once on unplugging
   ("the port failed (reading the reply to 01111)"), the port closed and
   the link went to "Adapter fault". The reopens failed "no such port"
   on the backoff (0.1, 0.2, 0.4, 0.8, 1.6, 3.2 s, then every 5 s), and
   the one after the plug went back in, 16.4 s after the failure,
   reopened COM4, ran the setup (echo back on: a power cycle) and went
   quiet again, with no reconnect. Nothing came unasked after the
   reopen: the VX prints nothing on power-up that reaches the port.
   Windows kept the name COM4.
4. **250 kbit/s:** protocol 8 took `OK`, and the session went quiet as at
   500 kbit/s, with the same 100 then 300 ms.
5. **The J2534 path after it** still connected, and went to "Requests
   failing" as the J2534 bench does with no bus.
6. **The labels:** quiet reads "Link quiet" on the header and the other
   pages, and "Vehicle not responding: quiet bus" on Live's banner, by
   design (`Theme.linkLabel`, `LiveViewPage.qml`); the run sheet named
   only the banner's.
