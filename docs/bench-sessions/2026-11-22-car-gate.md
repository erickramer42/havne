## Row 705: a module that answers nothing

**On the phone (events only).** The release APK gives no wire log
(Findings), so this reads from `signals.csv` and `events.log`. A session
reads one profile and an own signal set is a profile of its own, so the
set held the absent module's DID (`0x7E5`/`0x7ED`, `22 F40D`) and RPM as
an own signal (`01 0C` on `0x7E8`):
`profile=plugin.vehicle-1-signals.base`, 01:01:56-01:06:30. That profile
asks every signal whatever the Dashboard picks, so there is no baseline
without the absent module. `0x7ED` drew 58 timeouts in 274 s, no answer
and no link alarm, its gauge "waiting for data"; the backoff predicts
about 56 (0.5, 1, 2 and 4 s, then every 5 s), and one ask a lap would be
thousands. RPM beside it: P50 0.022 s, P99 0.113 s, max 0.324 s.

**On the VX (the wire log).** `profile=uds-generic`, the engine's four
DIDs (`03EC`, `0415`, `0520`, `1310` on `0x7E8`), `ECUIO_SUR_LOG_FRAMES=1`
in all three sessions (their rates compare with each other, not with B1):

| Session | Engine DIDs P50 / P99 / max (s) | Asks to `0x7E5` (`22 F40D`), all timed out |
|---|---|---|
| C1, `0x7E8` alone, 60 s, 01:16:35 | 0.026 / 0.041 / 0.086 | none |
| C2, plus `7ED:F40D`, hold on, 120 s, 01:17:38 | 0.040 / 0.055 / 0.076 | 27 |
| C3, plus `7ED:F40D`, `hold=0`, 60 s, 01:19:42 | 0.040 / 0.060 / 0.067 | 15 |

The excerpts' requests to `0x7E5` are the connect's identification read
(`09 02`) once, then `22 F4 0D` at gaps of 0.6 s (from the `09 02`), 1.0,
2.0 and 4.0 s, then 5.0 s every time (4.999-5.012 s), in both sessions;
the 27 and 15 asks count the same in the excerpts. The absent module's
DID stayed empty, with no alarm and no refusal, and `hold=0` still loses
B2's replies, so the hold hides nothing.

The engine's DIDs went from 0.026 s to 0.040 s with the absent module's
channel added: 1.54x and +14 ms, inside the sheet's "within 0.1 s" and
outside its "within 1.1x". The slowdown is flat (worst 0.076 s, no gap
near a timeout's length), the same with `hold=0`, and does not scale
with the absent module's asks. It looks like a second channel's cost on
the VX rather than the rule's; a control with a second answering module
would separate the two and was not run.

## Findings

1. **The phone's Dashboard had no transmission gauge** (nor any `0x769`
   or `0x72E` gauge), so A1 never asked `0x7E9` and was not v0.8.0's
   failing shape. A2 added it (pass) and removed it. The sheet's
   "transmission gauge on" item was not met by the layout as found.
2. **The release APK is not debuggable:** `run-as` is refused, so
   `phone.sh pull` gets no settings and no wire logs from a release
   build. The `AT SH` count and row 705's wire-log check cannot be read
   on the phone.
3. **A session reads one profile, and an own signal set is a profile of
   its own** that extends neither `obd2` nor the plugin. On the phone an
   own signal cannot sit beside the plugin's gauges (the gauge reads
   "needs Vehicle 1 signals"), so row 705's phone check needed its own
   RPM beside the absent DID.
4. **Row 705 on the VX:** the engine's DIDs 1.54x slower with the absent
   module's channel (above).
5. **Page 1 of the phone's Dashboard has three cells bound to signals
   outside this profile:** Engine Oil Temp (PID 5C, "not sent by this
   ECU"), "Engine oil pressure" and "Knock sensor, 1" ("not in KF
   dashboard (private)"). A layout matter, not a stall; page 3's oil
   pressure gauge reads.
6. **Two `0x7E8` values showed "no new data"** about 9 s into A1 before
   their first lap (above).
7. **A2 connected into the drive view** (the phone may now store
   `phoneDrive` as true), and the phone's Dash lists the extra Recent
   rows the run made. Neither was reverted: a release build gives no
   access to its settings file.
