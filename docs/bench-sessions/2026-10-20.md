# BENCH — informal session 2026-10-20 (VX, USB power, quiet bus, no vehicle)

**Context:** manual smoke of the link-health UI after the 2026-10-20
code-review and QML work. Not a formal sheeted session — no phase
plan, no soak. Adapter: OBDX Pro VX, USB powered, no OBD connector.

**URI:** `j2534://OBDX Pro - VX` (bare — the `obd2` default profile,
derived channel, no `?filter=` needed)

**App-visible result:** connected; LiveView/Home/Settings showed the
fault state ("Link: adapter fault (1 episode(s))" in the activity
log); clean disconnect. First BENCH-tier validation of the whole
link-health chain (vendor → worker health machine → bridge poll →
QML), and the first non-mock observation of the fault state.

## Findings against the BENCH prep list

- **Prep #1 — 4-byte filter shape: CONFIRMED.** The bare URI under
  `obd2` registers the 4-byte bare-ID FLOW_CONTROL shape
  (mask/pattern/flow-control all 4-byte big-endian CAN IDs), and the
  VX accepted it with logged vendor status 0. The 2026-10-16 session
  had only the 8-byte shape, accepted behaviorally. This is the
  shape's first hardware contact, and unlike 2026-10-16 the child now
  logs the vendor's filter status verbatim.
- **Prep #6 — empty-read status: OBSERVED, a third flavor.** The VX
  returns `STATUS_NOERROR` with zero messages for an empty read — not
  `ERR_BUFFER_EMPTY` and not `ERR_TIMEOUT`, so neither of the two
  statuses the read-status split names. Status 0 + empty frames reads
  as benign ("no frame") in practice — the session's fault state came
  from the writes, not the reads. Whether the VX ever pairs
  `ERR_TIMEOUT` with data remains a talking-bus question.
- **Writes on a no-ACK bus:** the first Mode-01 request succeeds
  (125 ms, status 0 — the 6-byte logical request shape, prep #2's
  first vendor-accepted send). Roughly 8 cycles later (938 ms) writes
  return `ERR_FAILED` (0x07) — hypothesis: with no other node on the
  bus nothing ACKs the CAN frames, the controller retransmits, and
  the vendor's TX queue backs up until it refuses. Expect this to
  vanish when an ECU ACKs; if writes still fail with a vehicle
  present, that is a real problem and a different diagnosis.
- **Finding-1 specimen (code review 2026-10-20):** the failing write
  returns `status 7, written 1` — a vendor reporting a nonzero count
  under a hard-error status. Exactly the case the count-trust rule
  must handle.
- **Teardown:** filter stop and disconnect both vendor status 0.

## Consequences

- The fault banner firing on real hardware within a ~1 s write-failure
  onset is the link-health design's intended unplugged-adapter
  behavior working end to end.
- The remaining pre-vehicle read-status unknowns are all talking-bus
  questions: `ERR_TIMEOUT`-with-data pairing, and write behavior with
  an ECU ACKing.
