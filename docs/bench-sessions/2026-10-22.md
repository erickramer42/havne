**Build:** `0a8beae`, both trees fresh (Win32 first; the app build
deployed the surrogate, byte-identical to `build-win32`'s). Suite
213/213 with the env-gated skip, cross-arch subset 25/25.
**Adapter:** OBDX Pro VX, USB powered, no OBD connector. The picker

**Why:** the [vehicle run sheet](vehicle-runsheet.md)'s pre-flight

**Session logs:** all six connects, paths normalized, in
[2026-10-22-surrogate.log](2026-10-22-surrogate.log). The recordings
aren't committed: no frame reached the bridge, so they hold only what

## Observations

1. **Requests as sent** (prep #2, the vendor side only): each write is
   `00 00 07 E0 01 <PID>`, TxFlags `0x40` (`ISO15765_FRAME_PAD`). The
   bare URI rotated `04 05 0C 0D 0F 11 2F 42 10 5C`.
2. **Writes on a bus with no other node: three, then refusal.** In all
   five request connects:
   - The first three writes returned status 0. Each was followed by a
     4-byte message, the CAN ID only, with RxStatus `0x00000009`
     (`TX_MSG_TYPE | TX_INDICATION`), stamped within about 1 ms of the
     write's return.
   - The fourth write, and every one after it (75 in all), blocked
     500–515 ms and returned `ERR_FAILED` (7) with "written 1", the
     untrusted-count specimen again. Each was followed by a 6-byte
     message echoing the request, RxStatus `0x00000201`, stamped at
     the moment the write returned. Bit `0x200` isn't among the
     v04.04 RxStatus bits in `j2534_ptypes.h`; its meaning is unchecked.
   - So the VX reports `TX_INDICATION` when it accepts a frame, not
     when the bus acknowledges it: nothing was there to acknowledge.
     It holds three unacknowledged frames, then refuses. That fits a
     transmit queue three frames deep that only an acknowledgement
     drains (some CAN controllers have exactly three transmit
     mailboxes), but nothing here confirms the mechanism. Each new
     connect accepted three writes again.
3. **Link health on hardware.** "Requests failing" latched at the
   first failed write, which returned 0.8 s after the filter in
   scheduler mode and 1.1–1.2 s with `?poll=`; the banner followed
   within the bridge's 100 ms tick. The probe interval grew as the
   backoff doubled from 100 ms to its 5 s cap, plus each blocked write
   and its read, and settled at 5.5 s (scheduler) and 5.6 s
   (`?poll=`). This is `ECUIO_ERR_REQUEST_FAILED`'s first sight on
   hardware; on 2026-10-20 the same setup showed "adapter fault",
   under the rules of the time. In B, with no writes, ten empty reads
   took the link quiet 1.42 s after connect: each read waited out its
   100 ms timeout and the worker slept 20 ms between reads.
4. **ReadMsgs statuses** (prep #6):
   - Empty: `ERR_BUFFER_EMPTY` (`0x10`, logged as status 16), after
     the read's full 100 ms timeout (B: the first read returned 106 ms
     after the filter, and the change-only summary logged no other
     status for the rest of the connect).
   - Short batch: every read in A and C–F asked for 16 messages and
     got one, an indication. The VX held each for its full timeout
     (the drain's 20 ms reads returned 23–37 ms after the write,
     `?poll=`'s 100 ms reads 101–117 ms) and returned
     `STATUS_NOERROR`, never `ERR_TIMEOUT`.
   - The surrogate drops indications before it counts, so each of
     those reads logs "status 0, frames 0". The 2026-10-20 note read
     that same line as the VX's empty-read status; its frames weren't
     logged then. Both statuses map to "no frame" in the client, so
     nothing changes in code.
5. **Timestamps** (prep #5): **microseconds.** The 75 failed-write
   indications in A and C–F, spanning 391 s, fit the host's
   write-return times with a slope of 1.0000003 vendor seconds per
   host second and residuals within about ±1 ms, the host stamps'
   resolution. The clock doesn't reset at open or connect. Its zero
   fell about six minutes before connect A, consistent with counting
   from power-up (the plug-in time wasn't noted). As a 32-bit count of
   microseconds it wraps 71.6 min after zero. These are indications;
   the vehicle session checks replies.
6. **Request cadence on the VX.** Scheduler: one request per 97–100 ms.
   `?poll=`: one per 203–227 ms, because poll mode's 100 ms read runs
   its full timeout before the 100 ms sleep. A single polled PID
   refreshes at about 4–5 Hz on this adapter.
7. **Recording (ADR-0017) on hardware.** Six folders, one per connect.
   Each `events.log` holds the URI, the signal set, "surrogate frame
   logging on, set by this recording", the link transition, both
   `Disconnecting:` and `Disconnected:`, and the summary "0 frames,
   0 values, 0 frames dropped by the bridge". `frames.csv` is its
   header row only, because indications never reach the bridge;
   `signals.csv` is its byte-order mark and header row. Each spawn's
   log reads "frame logging on (ECUIO_SUR_LOG_FRAMES=1)".
8. **Kept session logs.** Each new spawn kept the previous connect's
   log under the stamp of its last line, which matches that connect's
   `OP_DISCONNECT` to the millisecond; F's is still the current log.
9. **VBATT** (bench sheet Phase 3): surface absent. The transport
   issues no ioctls.

## Consequences for the vehicle session

- Phase 0 (ignition off) should repeat this run's request connects:
  three accepted writes, then status 7 after about 0.5 s, with the
  banner in under a second.
- Phase 1 goes quiet after about 1.4 s, not 1.2 s.
- Phase 2's `?poll=0x0C` refreshes RPM at about 4–5 Hz; that's this
  adapter's poll cadence, not a fault.
- An `rx 0x00000009` line after a write doesn't show that a request
  reached an ECU. Only a reply does.
- A session that runs more than about 70 minutes past the adapter's
  power-up sees `timestamp_us` wrap in `frames.csv`.
