Havne 0.3.3 reads cars through ELM327 adapters over USB, Bluetooth and WiFi, comes to Android phones as a signed download, remembers your vehicles and settings, and is QtTune's new name. Read [DISCLAIMER.md](https://github.com/erickramer42/havne/blob/main/DISCLAIMER.md) before connecting it to a vehicle.

## Try it

**Windows**

1. Download `havne-0.3.3-windows-x64.zip` below and unzip the whole folder.
2. Run `havne.exe`. The program isn't code-signed, so SmartScreen may stop it the first time: choose **More info**, then **Run anyway**.
3. In Settings, tick **Developer mode** under Display, then press the `mock://demo` preset under Adapter and **Connect**.

The zip's `README.txt` covers adapters and what each file is.

**Android 12 or later (64-bit ARM)**

1. On the phone, download `havne-0.3.3-android-arm64-v8a.apk` below and open it. Android asks to let your browser or file manager install apps the first time; Play Protect may offer to scan an app from outside Google Play.
2. Open Havne. In Settings, tick **Developer mode** under Display, then press the `mock://demo` preset under Adapter and **Connect**.

A later release installs over this one and keeps its settings and recordings. A Havne built by CI or from source carries another key, so uninstall it first.

## What's new since 0.3.2

**ELM327 adapters**
- **`elm327://<port>` reads a car through an ELM327-compatible adapter** ([ADR-0026](https://github.com/erickramer42/havne/blob/main/docs/adr/0026-elm327-transport.md)), such as an OBDLink or an OBDX Pro in its ELM mode: on a serial port (USB, or Bluetooth paired as a port: `COM5` on Windows, a `/dev/` path on macOS and Linux), or at a WiFi adapter's address once the computer has joined its network (`elm327://192.168.4.1:23` for an OBDX Pro, `elm327://192.168.0.10:35000` for most others; both are presets). It runs the same request engine, supported-PID probe and identification as J2534, with the `obd2` profile by default, and a dropped link recovers on its own. Settings lists the machine's serial ports beside the J2534 interfaces without opening any. How it works: [docs/elm327.md](https://github.com/erickramer42/havne/blob/main/docs/elm327.md).
- **A session that asks nothing listens:** `?profile=raw` without `?poll=` has the adapter monitor the bus for the engine ECU's messages (or `?filter=`'s ID), silently, so another tool's conversation can be logged and recorded.
- **Each connect writes a wire log** to the temporary folder (`ecuio-elm327.<date-time>.log`): every command and what the adapter answered, and while recording, every request and reply with its timing.
- **Lost frames are flagged:** when an adapter's buffer overflows (an ELM327's `BUFFER FULL`, a J2534 driver's `ERR_BUFFER_OVERFLOW`), the next frame says so in the recording, the activity log says so once, and the Log page's frame view counts them.

**Android**
- **A signed APK for Android 12 or later** comes with each release from this one on ([ADR-0030](https://github.com/erickramer42/havne/blob/main/docs/adr/0030-signed-android-releases.md)), so each later release installs over it and keeps the app's data.
- **Bluetooth through the phone** ([ADR-0028](https://github.com/erickramer42/havne/blob/main/docs/adr/0028-app-fed-streams.md)): Settings lists the phone's paired adapters, and **Scan for BLE** finds BLE ones. The session runs over the phone's Bluetooth as it would over a serial port, reconnecting on its own; Havne asks for the Nearby devices permission when the adapter list first opens.
- **Sessions keep running in the background** and with the screen off, recording included ([ADR-0029](https://github.com/erickramer42/havne/blob/main/docs/adr/0029-android-background-sessions.md)). A quiet notification says the session is connected, and the phone stays awake (not its screen) while it lasts. A `mock://` or `replay://` session may pause in the background.
- **Nothing of Havne's goes into the phone's backup** or a transfer to a new phone, since its preferences and recordings can hold the vehicle's VIN, and the notification and header show a Bluetooth adapter's address only by its last two parts.

**Vehicles and preferences**
- **Vehicles** ([ADR-0027](https://github.com/erickramer42/havne/blob/main/docs/adr/0027-vehicle-profiles.md)): pick a named vehicle in Settings before connecting, and it fills in that car's adapter, profile and DIDs, restores the signals plotted on Live, and names the recording's folder after it. The VIN recognizes a saved car at the next connect; only a salted hash of it is stored. New, Duplicate, Rename and Forget are buttons there.
- **Havne remembers** the last URI that connected, the Record sessions switch, units and zoom between runs, and each adapter's firmware versions as last seen at a connect, shown on its row without opening it.
- **Recent recordings** are listed in Settings, newest first; selecting one fills in its `replay://` address, with the profile and DIDs it was recorded with. A replay is never recorded again.

**The app**
- **Settings opens on the connect bar** and five folded sections (Adapter, Vehicle, What to read, Recording, Display), each heading saying what it holds; a row picked further down scrolls back to Connect.
- **The Log page is the activity log,** time-stamped, with a Copy button. **Developer mode**, a switch in Settings, adds the `mock://demo` preset and the raw frame table with its delivery counters.
- **Live's chart draws a crowded trace as a band**, the range it swings over, so a signal that swings every moment reads as one shape; ten signals get a color each before any repeats dashed.
- **An app icon** on Windows, Android and iOS, a dark title bar on Windows that takes the header's color on Windows 11, and a Home logo whose needle idles and blips into the red.

**The new name**
- **QtTune is now Havne:** the program is `havne.exe` and the repository `erickramer42/havne` (the old address redirects). The first launch copies QtTune's preferences, vehicles included, and Settings lists the recordings under `Documents\QtTune\recordings` beside the new `Documents\Havne\recordings`; neither is moved or deleted. On Android, Havne is a new app that starts empty.

**Fixes**
- An OBDLink MX+ whose reset answers twice over a new Bluetooth link no longer fails the connect, and a supported-PID query answered with another PID's reply is asked again.
- A J2534 driver reporting a buffer overflow on a read no longer reads as an adapter fault with the read's messages dropped.
- A WiFi adapter's network left behind says so in words, not a sockets error number.
- Settings no longer carries a replay's or the mock's options into an adapter's URI, and Settings, Home and the Dashboard fit a narrow window or a phone that turns.
- The full list is in the [CHANGELOG](https://github.com/erickramer42/havne/blob/main/CHANGELOG.md#033---2026-10-29).

## What's verified, and where

Havne's claims are tiered ([docs/testing.md](https://github.com/erickramer42/havne/blob/main/docs/testing.md)):

- **Every build** runs the full test suite on Windows, macOS and Linux in CI, plus sanitizers, fuzzing (the decoder, the validators, the URI parser, the ELM327 reply parsers and the replay reader), clang-tidy, CodeQL and, on Windows and Linux, the load test. The Android and iOS apps are cross-built there; their tests don't run on a device.
- **The J2534 stack** is verified end to end against an in-tree fake vendor driver, through both the 64-bit and the 32-bit helper (the 32-bit one on the development machine). **The ELM327 transport** is verified against a fake adapter behind its serial port (on Linux and macOS a pseudo-terminal), a TCP socket on every platform, and the phone's Bluetooth feed.
- **ELM327 on a car:** one car, read-only, from a Windows laptop, through an OBDLink MX+ over Bluetooth and an OBDX Pro VX in ELM mode over USB ([session sheet](https://github.com/erickramer42/havne/blob/main/docs/bench-sessions/2026-10-27-elm327-vehicle.md)). The VX's WiFi has carried a session on the bench ([bench-4](https://github.com/erickramer42/havne/blob/main/docs/bench-sessions/2026-10-27-elm327-bench-4.md)), and listening has run only on the bench, with no bus traffic to hear.
- **Android:** one phone (Android 16) on the same car, through the MX+ over classic Bluetooth, including in the background and with the screen off ([android-8](https://github.com/erickramer42/havne/blob/main/docs/bench-sessions/2026-10-28-android-8.md), [android-11](https://github.com/erickramer42/havne/blob/main/docs/bench-sessions/2026-10-28-android-11.md), [2026-10-29](https://github.com/erickramer42/havne/blob/main/docs/bench-sessions/2026-10-29-android.md)). Those runs used development builds. No BLE adapter has run.
- **This build itself hasn't connected to an adapter or a car.** A Release APK of this version, built locally and signed with the release key, has installed on the phone and run `mock://demo`. iOS hasn't run on a device. Other vehicles and adapters are untested.

## Verifying the downloads

`SHA256SUMS.txt` holds both downloads' SHA-256. Each also carries a signed build provenance from this repository's release workflow, attached as `<download>.intoto.jsonl`. Check them with the GitHub CLI:

```
gh attestation verify havne-0.3.3-windows-x64.zip -R erickramer42/havne
gh attestation verify havne-0.3.3-android-arm64-v8a.apk -R erickramer42/havne
```

The APK is signed with Havne's release key, whose certificate SHA-256 is `fb4f415a1f6c0dc56ee54dcd454c29d2226bc293c7b4c978a9b9bc8e74c4210f` ([packaging/android/release-cert.sha256](https://github.com/erickramer42/havne/blob/main/packaging/android/release-cert.sha256)). With the Android SDK's build tools, `apksigner verify --print-certs havne-0.3.3-android-arm64-v8a.apk` prints it.
