QtTune 0.3.2 plays recorded sessions back on any platform, decodes values in the core as each frame arrives, and runs every vendor driver in a process of its own. Read [DISCLAIMER.md](https://github.com/erickramer42/qttune/blob/main/DISCLAIMER.md) before connecting it to a vehicle.

## Try it

1. Download `qttune-0.3.2-windows-x64.zip` below and unzip the whole folder.
2. Run `qttune.exe`. The program isn't code-signed, so SmartScreen may stop it the first time: choose **More info**, then **Run anyway**.
3. In Settings, press the `mock://demo` preset, then **Connect**.

The zip's `README.txt` covers adapters and what each file is.

## What's new since 0.3.1

**Replay**
- **`replay://<recording folder>`** plays a recorded session's frames back at their own pace, up to 100 times faster, or as fast as the app can take them, optionally looping, on every platform ([ADR-0023](https://github.com/erickramer42/qttune/blob/main/docs/adr/0023-replay-transport.md)). Record a session with Settings' **Record sessions** switch, then replay it without the car; add `?profile=obd2` to decode a J2534 recording. If the recording changes while it plays, playback stops and says so.

**Values and timing**
- **Decoding runs in the core, on the transport's thread,** not in the UI ([ADR-0024](https://github.com/erickramer42/qttune/blob/main/docs/adr/0024-decode-on-the-worker.md)): a frame dropped under load still delivers its values to the pages and the recording.
- **Short peaks stay:** Live's strip chart plots each value at its own frame's time and keeps each 100 ms window's highest and lowest, and the Dashboard's peak and low holds catch them too. A recorded engine start replayed fast had shown a peak of 1,195 rpm against the recording's 1,261.
- **Each session ends with its delivery figures** in the activity log: frames received and dropped, and how long frames took to reach the app and values to reach its pages.

**Adapters**
- **Every J2534 driver runs in a helper process of its own architecture** ([ADR-0025](https://github.com/erickramer42/qttune/blob/main/docs/adr/0025-one-j2534-backend.md)): 64-bit drivers in the new `ecuio-j2534-surrogate-x64.exe`, 32-bit ones in `ecuio-j2534-surrogate.exe`, both beside `qttune.exe`. A driver that crashes ends its helper, not QtTune, and the session reports an adapter fault.
- **A raw session listens to the engine ECU** without `?filter=`, and `?profile=raw&poll=` asks it.
- **Connect failures name a vendor's status in hex** as well as decimal.

**Fixes**
- A link failure's log line always counts its own episode, a URI pasted with spaces around it connects, and the first frame of a session is never lost to the connect.
- The strip chart stays sharp under zoom and its labels fit a short plot, Live keeps the chart on screen on a short page, and the Log page frees long replies' memory once short frames replace them.
- The full list is in the [CHANGELOG](https://github.com/erickramer42/qttune/blob/main/CHANGELOG.md#032---2026-10-26).

**Engineering**
- **A load test on every CI run:** a recorded engine start replays through the app's bridge on Windows and Linux, and the run fails if a frame goes unaccounted for or the recording's peak is lost. On the development machine the worker sustains about 400,000 frames a second through decode, and frames reach the UI thread in under a quarter of a millisecond at the median ([docs/testing.md](https://github.com/erickramer42/qttune/blob/main/docs/testing.md#load-test-the-replay-fixture-through-the-bridge)).
- clang-tidy gates the core and the surrogate in CI, CodeQL scans them, and the download's signed provenance is a release file too.
- Each executable carries a version resource (Explorer's **Details** tab), and the release build refuses one whose version isn't the release's.

## What's verified, and where

QtTune's claims are tiered ([docs/testing.md](https://github.com/erickramer42/qttune/blob/main/docs/testing.md)):

- **Every build** runs the full test suite on Windows, macOS and Linux, plus sanitizers, fuzzing, clang-tidy and, on Windows and Linux, the load test, in CI. Everything above passes it.
- **The J2534 stack** is verified end to end against an in-tree fake vendor driver, through both the 64-bit and the 32-bit helper (the 32-bit one on the development machine; CI runs only 64-bit).
- **One real adapter** (an OBDX Pro VX) has read **one car**, read-only, in two sessions. The second ([session sheet](https://github.com/erickramer42/qttune/blob/main/docs/bench-sessions/2026-10-25-vehicle.md)) ran 0.3.1's request engine, supported-PID probe, identification and `uds-generic` on the car. Its recordings and the first session's, replayed through this release's decoding, give back every value decoded in the car: 24,632 of them.
- **This build itself hasn't connected to an adapter or a car.** No real 64-bit driver has run through the new 64-bit helper: the VX's driver is 32-bit. Other vehicles and adapters are untested.

## Verifying the download

`SHA256SUMS.txt` holds the zip's SHA-256. The zip also carries a signed build provenance from this repository's release workflow, attached as `qttune-0.3.2-windows-x64.zip.intoto.jsonl`. Check it with the GitHub CLI:

```
gh attestation verify qttune-0.3.2-windows-x64.zip -R erickramer42/qttune
```
