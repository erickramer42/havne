Havne 0.3.6 names a car's trouble codes, decodes its VIN and says whether it would pass an emissions inspection, clears codes with the engine running, simulates an ECU on Linux's virtual CAN bus, and relays a phone's Bluetooth adapter to a computer; the features from 0.3.5 have now run on a car through both adapters on hand. Read [DISCLAIMER.md](https://github.com/erickramer42/havne/blob/main/DISCLAIMER.md) before connecting it to a vehicle.

## Try it

**Windows**

1. Download `havne-0.3.6-windows-x64.zip` and unzip the whole folder.
2. Run `havne.exe`. The program isn't code-signed, so SmartScreen may stop it the first time: choose **More info**, then **Run anyway**.
3. In Settings, tick **Developer mode** under Display, then press the `mock://demo` preset under Adapter and **Connect**.

The zip's `README.txt` covers adapters and what each file is. `havne-cli.exe` is beside `havne.exe`: `havne-cli stream mock://demo --values --count 20` prints a simulated car's frames and values.

**Linux (x86_64, glibc 2.39 or later: Ubuntu 24.04 and newer, Debian 13, Fedora 40 and newer, Arch)**

1. Download `havne-0.3.6-linux-x86_64.AppImage`.
2. `chmod +x havne-0.3.6-linux-x86_64.AppImage`, then run it.
3. In Settings, tick **Developer mode** under Display, then press the `mock://demo` preset under Adapter and **Connect**.

It takes OpenGL, fonts and FUSE from the system; a minimal install may lack them. [docs/linux.md](https://github.com/erickramer42/havne/blob/main/docs/linux.md) says what to install, how to reach an adapter (serial permissions, Bluetooth, SocketCAN) and where Havne keeps its files.

For `havne-cli` and the core alone: `sudo apt install ./havne-core_0.3.6_amd64.deb`, or unpack `havne-core-0.3.6-linux-x86_64.tar.gz` anywhere.

**Android 12 or later (64-bit ARM)**

1. On the phone, download `havne-0.3.6-android-arm64-v8a.apk` and open it. Android asks to let your browser or file manager install apps the first time; Play Protect may offer to scan an app from outside Google Play.
2. Open Havne. In Settings, tick **Developer mode** under Display, then press the `mock://demo` preset under Adapter and **Connect**.

A later release installs over this one and keeps its settings and recordings. A Havne built by CI or from source carries another key, so uninstall it first.

## What's new since 0.3.5

**Diagnostics, finished**
- **Trouble codes by name** ([ADR-0044](https://github.com/erickramer42/havne/blob/main/docs/adr/0044-trouble-code-titles.md)): the Diagnostics page shows SAE J2012's title beside each generic powertrain and network code ("P0301  Cylinder 1 Misfire Detected") and the freeze frame's, and **Look up a code** names a typed one, offline. `havne-cli dtc <code>` does the same.
- **The VIN decoded on the device** ([ADR-0043](https://github.com/erickramer42/havne/blob/main/docs/adr/0043-vin-decode.md)), with nothing sent anywhere: the model year, the make and whether the check digit matches. The activity log adds a `VIN:` line, Settings has **Look up a VIN**, and `havne-cli vin <VIN>` does the same.
- **Inspection readiness** ([ADR-0045](https://github.com/erickramer42/havne/blob/main/docs/adr/0045-inspection-readiness.md)): the Diagnostics page says whether the car would pass the federal OBD inspection rule (40 CFR 85.2222) today, from every ECU's monitors and check-engine light and the model year in its VIN, and names the monitors still incomplete. A state's program may be stricter.
- **This drive cycle's readiness** (PID 41) beside each monitor's state since the last clear.
- **Clearing with the engine running:** the confirmation says a clear works best with the engine off and the ignition on, and clears with it running on your word; an ECU that refuses says so on its card. If the car is moving, the page asks once more, naming the speed. When no codes are stored, the confirmation says what a clear would still reset.

**The simulated ECU** ([ADR-0046](https://github.com/erickramer42/havne/blob/main/docs/adr/0046-simulated-ecu.md))
- `havne-cli sim mock://sim --on vcan0` answers OBD-II requests on Linux's virtual CAN bus as the simulated car's engine ECU, so `havne-cli stream "socketcan://vcan0?profile=obd2"` or the app reads values, identification and trouble codes with no hardware. `havne-cli sim replay://<recording> --on vcan0` answers as the car in a recording did.

**The phone as a relay** ([ADR-0047](https://github.com/erickramer42/havne/blob/main/docs/adr/0047-adapter-relay.md))
- The Android app relays a paired Bluetooth adapter to a computer on the phone's USB cable, so `havne-cli` reaches an adapter only the phone can: in developer mode, select the adapter and press **Relay**, then `adb forward tcp:35000 tcp:35000` and `elm327://127.0.0.1:35000` on the computer. It listens on the phone alone, takes one computer at a time and keeps running with the screen off.

**Faster**
- **A faster DID scan:** `?scan=first` under `profile=uds-generic` asks a `did=` range back to back before polling what it found, about 30 DIDs a second on the test car; `havne-cli stream` writes a `scan` line and `--until-scanned` ends the stream once every range is asked.
- **Through a J2534 adapter on Windows,** values refresh about a third more often: the driver's process holds Windows' 1 ms timer, so a reply is seen within the read's wait rather than Windows' 15.6 ms step. On the test car through the OBDX Pro VX, 28 % more replies arrived in the same time.

**For programs on the C ABI**
- `ecuio/vin.h` and `ecuio/sim.h`, trouble-code titles (`ecuio_dtc_parse`, `ecuio_dtc_title`), inspection readiness (`ecuio_diag_inspect`), this drive cycle's monitors in the diagnostics report, and a clear on the caller's word (`ecuio_session_clear_diagnostics_with`).

**Fixes**
- After an ignition cycle with a session connected, values refreshed at about a third of their rate for the rest of the session; asking several PIDs per request now resumes once the car answers again.
- A request to every ECU at once (`?txid=0x7DF`) now gets a reply longer than one CAN frame, such as the VIN, through a J2534 adapter or SocketCAN.
- A DID scan through a J2534 adapter could stop one DID short and never finish; a scanned DID's late reply now counts it found.
- Over an ELM327 adapter, the first reading of a PID whose reply spans two CAN frames (PID 68) was lost.
- On a phone: Live, the frame table and the clear's confirmation fit the screen, and tapping Disconnect while an adapter's replies arrive over Bluetooth no longer can crash the app.
- `havne-cli` ends a connect that hasn't finished within 60 s, with an `error` line and exit code 3.
- The driver process's per-session logs on Windows are kept to the newest 50, as the others are.
- The full list is in the [CHANGELOG](https://github.com/erickramer42/havne/blob/main/CHANGELOG.md#036---2026-11-02).

## What's verified, and where

Havne's claims are tiered ([docs/testing.md](https://github.com/erickramer42/havne/blob/main/docs/testing.md)):

- **Every build** runs the full test suite on Windows, macOS and Linux in CI, plus sanitizers, fuzzing, clang-tidy (over the app and `havne-cli` too), CodeQL, the load test on Windows and Linux, and a check of the C ABI against 0.3.5's. The Android and iOS apps are cross-built there; their tests don't run on a device.
- **Against the fakes and the simulated bus:** the titles, the VIN decode and inspection readiness at UNIT and in the app's and `havne-cli`'s tests; the simulated ECU on Linux's `vcan0`, through core's ISO-TP, as the mock's car and as the test car's recording; the relay on the desktop against a fake adapter; each fix pinned by a test that fails without it.
- **On the test car** (development builds before this release), through both adapters:
  - The OBDX Pro VX over J2534 on a laptop: several PIDs per request, 2.7 times as many replies a minute and RPM 2.8 times as often; two ECUs answering, both to a request to every ECU; the 1 ms timer in an A/B of four runs; then the fixes above re-run on the car: a request to every ECU got the VIN, both DID blocks completed, and packing came back after a key cycle; the VIN decoded and inspection readiness read "ready" ([2026-11-01](https://github.com/erickramer42/havne/blob/main/docs/bench-sessions/2026-11-01-vehicle.md), [2026-11-02](https://github.com/erickramer42/havne/blob/main/docs/bench-sessions/2026-11-02-vehicle.md)).
  - The OBDLink MX+ on the test phone (Android 16), relayed to a computer: the relay, two ECUs, a 1,024-DID block in 32.9 s and a sweep of the engine ECU's DIDs with the screen off for 36 minutes; Disconnect while replies arrived, 20 times without a crash; and the first clears on a car, with the engine off and running, on a car with no codes stored ([2026-11-01](https://github.com/erickramer42/havne/blob/main/docs/bench-sessions/2026-11-01-android.md)).
- **On the test phone** (Android 16): CI's Android build of this release's code, and then the dry run's APK (`v0.3.6-rc1`, signed with the release key), each installed and connected `mock://demo`.
- **These downloads, checked as published** (and in a full dry run, `v0.3.6-rc1`, before them): the checksums and provenance verify for every file, and the SBOM's attestation for the zip, the APK, the AppImage, the deb and the tarball; the zip holds the app, `havne-cli`, both J2534 helpers, the disclaimer, license and readme, and the symbols zip their four PDBs; the APK is version 0.3.6, not debuggable, and signed with the pinned release key. On Linux (Ubuntu 26.04 under WSL) the deb's `havne-cli` streamed the simulated car, its debug info matched by build ID, and the AppImage started.
- **Not yet run:** a car with a code stored, so a code erased by a clear; a clear through the VX; a second car; SocketCAN through a real CAN controller or on a car; the values beside a second scan tool's. This build itself hasn't connected to an adapter or a car. The iPhone app hasn't run on a device.

## Verifying the downloads

`SHA256SUMS.txt` holds every download's SHA-256, the debug files' and the SBOM's. One signed build provenance from this repository's release workflow covers every download, attached as `havne-0.3.6.intoto.jsonl`. Check them with the GitHub CLI:

```
sha256sum -c --ignore-missing SHA256SUMS.txt
gh attestation verify havne-0.3.6-windows-x64.zip -R erickramer42/havne
gh attestation verify havne-0.3.6-android-arm64-v8a.apk -R erickramer42/havne
gh attestation verify havne-0.3.6-linux-x86_64.AppImage -R erickramer42/havne
gh attestation verify havne-core_0.3.6_amd64.deb -R erickramer42/havne
```

Those read GitHub's attestation store; add `--bundle havne-0.3.6.intoto.jsonl` to check against the attached file instead.

The SBOM, `havne-0.3.6.spdx.json`, is attested to the zip, the APK, the AppImage, the deb and the tarball: add `--predicate-type https://spdx.dev/Document/v2.3` to check it.

The APK is signed with Havne's release key, whose certificate SHA-256 is `fb4f415a1f6c0dc56ee54dcd454c29d2226bc293c7b4c978a9b9bc8e74c4210f` ([packaging/android/release-cert.sha256](https://github.com/erickramer42/havne/blob/main/packaging/android/release-cert.sha256)). With the Android SDK's build tools, `apksigner verify --print-certs havne-0.3.6-android-arm64-v8a.apk` prints it.

## Third-party data

Havne's core carries data from others, each under its own terms, listed in [core/THIRD_PARTY_NOTICES.txt](https://github.com/erickramer42/havne/blob/main/core/THIRD_PARTY_NOTICES.txt), which the Windows zip and core's packages ship, and compiled into every binary:

- Trouble-code titles: SAE J2012's generic powertrain and network codes, from [Wal33D/dtc-database](https://github.com/Wal33D/dtc-database) (MIT).
- Vehicle makes: the manufacturer codes of NHTSA's [vPIC](https://vpic.nhtsa.dot.gov/downloads/), a work of the US government.
