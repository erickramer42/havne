Havne 0.9.0 reads a whole car: a profile may hold every module's signals (up to 32 modules), the app asks only the signals you pick, and the pacing through J2534, ELM327 and SocketCAN adapters is reworked so each signal updates at about the same rate and a silent module no longer slows the others. It adds computed signals to the signal form, keyed recordings, Dashboard presets, `havne-cli`'s log report, and a simulated ECU that answers at a car's pace. Read [DISCLAIMER.md](https://github.com/erickramer42/havne/blob/main/DISCLAIMER.md) before connecting it to a vehicle.

## Try it

**Windows**

1. Download `havne-0.9.0-windows-x64.zip` and unzip the whole folder.
2. Run `havne.exe`. The program isn't code-signed, so SmartScreen may stop it the first time: choose **More info**, then **Run anyway**.
3. Press **Demo data** on Home, then **Connect**.

The zip's `README.txt` covers adapters and what each file is. `havne-cli.exe` is beside `havne.exe`: `havne-cli stream mock://demo --values --count 20` prints a simulated car's frames and values.

**Linux (x86_64 or 64-bit ARM, glibc 2.39 or later: Ubuntu 24.04 and newer, Debian 13 and Raspberry Pi OS 13, Fedora 40 and newer, Arch)**

1. Download `havne-0.9.0-linux-x86_64.AppImage`, or on 64-bit ARM (a Raspberry Pi 3 or later on a 64-bit system) `havne-0.9.0-linux-aarch64.AppImage`.
2. `chmod +x` it, then run it.
3. Press **Demo data** on Home, then **Connect**.

It takes OpenGL, fonts and FUSE from the system; a minimal install may lack them. [docs/linux.md](https://github.com/erickramer42/havne/blob/main/docs/linux.md) says what to install, how to reach an adapter (serial permissions, Bluetooth, SocketCAN) and where Havne keeps its files.

For `havne-cli` and the core alone: `sudo apt install ./havne-core_0.9.0_amd64.deb` (`./havne-core_0.9.0_arm64.deb` on ARM), or unpack `havne-core-0.9.0-linux-x86_64.tar.gz` (`havne-core-0.9.0-linux-aarch64.tar.gz`) anywhere.

**Android 12 or later (64-bit ARM)**

1. On the phone, download `havne-0.9.0-android-arm64-v8a.apk` and open it. Android asks to let your browser or file manager install apps the first time; Play Protect may offer to scan an app from outside Google Play.
2. Open Havne. On Dash, press the **Demo data** row, then **Connect**.

A later release installs over this one and keeps its settings and recordings. A Havne built by CI or from source carries another key, so uninstall it first.

## What's new since 0.8.0

**A whole car's signals**
- **A set may declare 32 modules** (4 before), so a signal file, a plugin, an OBDb import and `uds-generic`'s `?did=` take up to 32 ECUs. Each module may be asked up to 1024 requests, and a plugin variant may hold 16,384 signals ([ADR-0065](https://github.com/erickramer42/havne/blob/main/docs/adr/0065-car-sized-profile.md)).
- **Havne asks at most 1024 requests at a time.** On a car-sized profile it asks only the signals you pick (ticked on Live, placed as gauges, or read by a condition) and says so in the log; `havne-cli log` without `--signal` or `--conditions` stops with a message instead of recording nothing.
- **Recordings are format 4: a signal's values are kept under its key**, so two signals of one name stay two. Older recordings open as before; a Havne before this one reads a format 4 recording with keys shown as names. `havne-cli`'s `--signal` takes a key or a name one signal has, and refuses a name two signals share with their keys listed. A vehicle's ticks on Live are kept by key too.
- **Breaking for a reader by position:** the long CSV export gains a last column, `key`. A reader that goes by the named columns is unaffected. CSV exports now start with a UTF-8 byte order mark so Excel shows units such as the degree sign correctly: read them with encoding `utf-8-sig` in Python or `fileEncoding = "UTF-8-BOM"` in R.

**Pacing and quiet modules**
- **Through J2534 with several modules**, each signal is read about as often as every other, long replies no longer cost another module its reply, and modules that aren't in the car no longer slow the others, with long replies beside them too. On a simulated four-module car the slowest signal updates every 0.72 s where it took 1.57 s, and the car's values a second rise from 103 to 137.
- **Through ELM327**, a pick spread over several ECUs no longer starves the engine's values: each ECU is asked each of its requests in turn, and a module that is off, asleep or not fitted no longer costs the others a NO DATA on every lap. A `?session=03` keep-alive goes out when it falls due. A connect beside 14 absent modules shows the others' first values in about 5 s where it took about 13 s.
- **A silent module is probed with growing waits** (0.5, 1, 2, 4 s, then every 5 s) while another module answers, and its identification and diagnostics wait until it does. A module switched off and on again is read again within about 5 s on every adapter, SocketCAN included; one that was off from the connect is too, except through a J2534 adapter beside long replies, where it can take up to about 40 s.
- **If the computer sleeps during a session,** the wire log says so, including when a request was out and its reply is lost, where it read as an adapter gone quiet for 5 s ([ADR-0033](https://github.com/erickramer42/havne/blob/main/docs/adr/0033-session-time-counts-sleep.md)).
- A J2534 adapter whose frame timestamps stand still, or count frames and not microseconds, no longer stalls a session's frame times.
- The OBDX Pro VX in J2534 mode, which loses a second module's single-frame reply that arrives beside another module's long one, is now waited out (`?hold=0` turns it off).
- These pacing figures are measured on a simulated car and adapter, and none is yet confirmed on a car: see "What's verified".

**Signals and Dashboard**
- **Computed signals in the signal form:** write an expression, see it checked as you type, pick the signals it reads, try values (or fill them from the connected session) and save it into your vehicle's own signals. `havne-cli signals expr` checks an expression before it is written.
- **Dashboard presets:** Standard, Temperatures and Showcase join Blank page and From a file in the "+" tab's list; "Replace this page with..." puts a preset on the shown page. A plugin can carry Dashboard pages for the form of your window. Each is one undo step.
- A gauge whose signal the car doesn't send says so, a new gauge's guessed range says so, and a computer's edit mode has a **Phone layout** switch to build a phone's layout at the desk.
- **The viewer** moves a plotted signal to another pane and keeps the arrangement for each recording. A pull now ends at the throttle's lift, so a run onto the limiter includes the limiter and its fuel cut; **A pull ends** in the Stretches panel gives the earlier rule.
- Live lists the signals it hides, each with its reason, and a replay's rows that the recording lacks read "Not in this recording".

**Tools, the simulated ECU and the library**
- `havne-cli log` ends with an `interval` line for each signal (values with P50, P99, minimum and maximum) and a `summary` line, counted from the moment every answering signal had answered, so any car and adapter is measured the same way.
- **The simulated ECU can answer at a car's pace** (`delay=`, `fc=`, `cf=`, `seed=`), be busy (`busy=`), share a bus (`bus=`) and have its faults aimed at one module (`@<reply ID>`). `example-car`, a made-up car of 18 modules, is a second example plugin that `havne-cli plugins check` reads with no car.
- A plugin's manifest may be format 2 with a conversation part: Havne reads and checks it and runs no module in this version.
- **C API:** a signal's key (`ecuio_signal_key_t`) with `ecuio_signal_address_key`, `ecuio_signal_set_keys` and `ecuio_signal_set_find`; the set's layout is 5 (breaking: `ecuio_channel_decl_t` is 16 bytes, so a set built by hand is rebuilt against the header); `ECUIO_SIM_MAX_REPLIES` is 66; `ECUIO_PROFILE_MAX_REQUESTS` means the rotation's size, not what a set defines. Python gains `SignalFile.keys()`, `key_of`, `check_expr`, `expr_ref`, `evaluate` and `Plugin.pages()`. The full list is in the [CHANGELOG](https://github.com/erickramer42/havne/blob/main/CHANGELOG.md#090---2026-11-21).
- **Windows builds are reproducible:** building a release commit again gives byte-identical program files and the same zip (the symbols zip differs).

**Fixes**
- A paused Live chart drew almost none of its samples; it now draws every column and paints faster.
- A connect error that quotes an adapter's reply is drawn as text, so an adapter can no longer make Windows open a network share from it.
- A signal file that no vehicle lists shows as "A signal file" on the Settings page, where its row was a lone colon.
- A signal file kept from an earlier version that no vehicle used stays after the update, with Save and Remove, instead of being deleted at the next start.
- A DID scan whose reply was lost on a healthy link asks that DID once more, so `?did=` scans complete.
- A recording that fails to open no longer leaves an empty folder on the Recordings page.
- Running out of memory while a session is created no longer leaves an adapter's port open.
- A connected car's VIN no longer switches the picked vehicle during a session; the vehicle it names is offered for the next connect.
- A rare crash in the Dashboard's edit mode after adding and removing a page is fixed.

**Moving from v0.8.0.** After an update from a version before v0.8.0, the vehicle list and signal files that version kept are removed at the second start, once the first has moved them into the plugin store; a signal file that could not be moved stays until you save or remove it. Going back past v0.8.0 then shows no vehicles or signal files, and going back to v0.7.x after the move is not supported.

## What's verified, and where

Havne's claims are tiered ([docs/testing.md](https://github.com/erickramer42/havne/blob/main/docs/testing.md)):

- **Every build** runs the full test suite on Windows, macOS and Linux in CI, plus sanitizers, fuzzing, clang-tidy, CodeQL and the load test; a GCC or Clang warning fails it. The release pull request's run on this release's commit gates the tag.
- **Locally** the full verify at the release commit passed 3491 of 3491 tests, and the cross-arch (x86) step passed 127 of 127. The skipped cases are the ones gated on what a Windows machine lacks (Linux, Wireshark's `tshark`, the car's raw recordings).
- **Pacing:** the simulated-ECU model is held within 10% of five of the car's one-module runs of 2026-11-18 (the MX+ within 5%); it doesn't yet match the car's runs with no gap between requests or with two modules through the VX. The simulated figures above are the model's, not a car's.
- **On a phone:** the release candidate's APK was installed over 0.8.0's on the test phone, keeping its settings and recordings, before the car run below.
- **On a car:** the release was tagged only once its release candidate had run in the car with every gauge updating at its rate: on the phone with an OBDLink MX+, the transmission's gauge on a four-channel Dashboard, and on a laptop with an OBDX Pro VX over J2534, the hold on. A module switched off beside the engine's gauges left the others at their pace, and its values came back within about 5 s of switching it on. The pacing figures under "What's new" are still the simulated car's.
- **Not yet run:** the iPhone app has not run on a device. The car ran the release candidate's downloads, built from the same commit as these.

## Verifying the downloads

`SHA256SUMS.txt` holds every download's SHA-256, the debug files' and the SBOM's. One signed build provenance from this repository's release workflow covers every download, attached as `havne-0.9.0.intoto.jsonl`. Check them with the GitHub CLI:

```
sha256sum -c --ignore-missing SHA256SUMS.txt
gh attestation verify havne-0.9.0-windows-x64.zip -R erickramer42/havne
gh attestation verify havne-0.9.0-android-arm64-v8a.apk -R erickramer42/havne
gh attestation verify havne-0.9.0-linux-x86_64.AppImage -R erickramer42/havne
gh attestation verify havne-core_0.9.0_amd64.deb -R erickramer42/havne
gh attestation verify havne-0.9.0-py3-none-win_amd64.whl -R erickramer42/havne
```

Those read GitHub's attestation store; add `--bundle havne-0.9.0.intoto.jsonl` to check against the attached file instead.

The SBOM, `havne-0.9.0.spdx.json`, is attested to the zip, the APK, the AppImages, the debs, the tarballs and the wheels: add `--predicate-type https://spdx.dev/Document/v2.3` to check it.

The APK is signed with Havne's release key, whose certificate SHA-256 is `fb4f415a1f6c0dc56ee54dcd454c29d2226bc293c7b4c978a9b9bc8e74c4210f` ([packaging/android/release-cert.sha256](https://github.com/erickramer42/havne/blob/main/packaging/android/release-cert.sha256)). With the Android SDK's build tools, `apksigner verify --print-certs havne-0.9.0-android-arm64-v8a.apk` prints it.

## Third-party data

Havne's core carries data from others, each under its own terms, listed in [core/THIRD_PARTY_NOTICES.txt](https://github.com/erickramer42/havne/blob/main/core/THIRD_PARTY_NOTICES.txt), which core's packages ship and every download's notice repeats, and compiled into every binary:

- Trouble-code titles: SAE J2012's generic powertrain and network codes, from [Wal33D/dtc-database](https://github.com/Wal33D/dtc-database) (MIT).
- Vehicle makes: the manufacturer codes of NHTSA's [vPIC](https://vpic.nhtsa.dot.gov/downloads/), a work of the US government.
