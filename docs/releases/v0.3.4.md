Havne 0.3.4 comes to Linux as an AppImage, adds `havne-cli` for scripts and terminals, listens to native CAN buses through SocketCAN, and ships its core as packages for your own programs, with debug symbols and an SBOM for every download. Read [DISCLAIMER.md](https://github.com/erickramer42/havne/blob/main/DISCLAIMER.md) before connecting it to a vehicle.

## Try it

**Windows**

1. Download `havne-0.3.4-windows-x64.zip` below and unzip the whole folder.
2. Run `havne.exe`. The program isn't code-signed, so SmartScreen may stop it the first time: choose **More info**, then **Run anyway**.
3. In Settings, tick **Developer mode** under Display, then press the `mock://demo` preset under Adapter and **Connect**.

The zip's `README.txt` covers adapters and what each file is. `havne-cli.exe` is beside `havne.exe`: `havne-cli stream mock://demo --values --count 20` prints a simulated car's frames and values.

**Linux (x86_64, glibc 2.39 or later: Ubuntu 24.04 and newer, Debian 13, Fedora 40 and newer, Arch)**

1. Download `havne-0.3.4-linux-x86_64.AppImage` below.
2. `chmod +x havne-0.3.4-linux-x86_64.AppImage`, then run it.
3. In Settings, tick **Developer mode** under Display, then press the `mock://demo` preset under Adapter and **Connect**.

It takes OpenGL, fonts and FUSE from the system; a minimal install may lack them. [docs/linux.md](https://github.com/erickramer42/havne/blob/main/docs/linux.md) says what to install, how to reach an adapter (serial permissions, Bluetooth, SocketCAN) and where Havne keeps its files.

For `havne-cli` and the core alone: `sudo apt install ./havne-core_0.3.4_amd64.deb`, or unpack `havne-core-0.3.4-linux-x86_64.tar.gz` anywhere.

**Android 12 or later (64-bit ARM)**

1. On the phone, download `havne-0.3.4-android-arm64-v8a.apk` below and open it. Android asks to let your browser or file manager install apps the first time; Play Protect may offer to scan an app from outside Google Play.
2. Open Havne. In Settings, tick **Developer mode** under Display, then press the `mock://demo` preset under Adapter and **Connect**.

This release installs over 0.3.3 and keeps its settings and recordings. A Havne built by CI or from source carries another key, so uninstall it first.

## What's new since 0.3.3

**Linux**
- **An AppImage for the desktop app** ([ADR-0035](https://github.com/erickramer42/havne/blob/main/docs/adr/0035-linux-downloads-sbom-reproducible.md)), built on Ubuntu 24.04, carrying Qt and its QML modules. Every transport but J2534 runs on Linux: ELM327 adapters over USB, Bluetooth (through `rfcomm`) and WiFi, replays, the simulated car and SocketCAN. A guide for Linux users: [docs/linux.md](https://github.com/erickramer42/havne/blob/main/docs/linux.md).
- **SocketCAN, listening** ([ADR-0032](https://github.com/erickramer42/havne/blob/main/docs/adr/0032-socketcan-listening.md)): `socketcan://can0` reads a native CAN interface (a candleLight or CANable adapter, PEAK, Kvaser, a Raspberry Pi's CAN hat) and sends nothing: every frame on the bus, or the IDs `?filter=` names, CAN FD and error frames included (an error frame is reported, never decoded as values), timed by the kernel. Bring the interface up first at the bus's bit rate and in listen-only mode (`sudo ip link set can0 up type can bitrate 500000 listen-only on`); Havne refuses one that could transmit and says how to fix it. Settings lists the CAN interfaces. Requesting profiles (`obd2`, `uds-generic`) don't run on SocketCAN yet.
- **A simulated car on a virtual CAN bus:** `havne-cli play mock://demo --to vcan0` puts the simulated car's frames on Linux's `vcan0`, where `socketcan://vcan0?profile=mock` (or any SocketCAN tool) can listen, with no hardware. It writes only to virtual interfaces, never to a real bus.
- **USDT probes:** core marks a session's start and close and each frame (`ecuio:session_start`, `session_close`, `frame`), so `bpftrace` and `perf` can count and time the frame path of a running Havne or `havne-cli` with no debug build.

**`havne-cli`, a command-line client**
- **`havne-cli stream <uri>`** ([ADR-0031](https://github.com/erickramer42/havne/blob/main/docs/adr/0031-command-line-client.md)) opens any session the app can (`mock://`, `replay://`, `elm327://`, `socketcan://`, and `j2534://` on Windows) and writes its frames as JSON lines, one object per line, for `jq`, scripts and logging without a desktop; `--values` adds the values the profile decodes. It stops at Ctrl+C, after `--count` frames or `--seconds`, at a replay's last frame, or when a replay stops early because its recording changed, and always ends with an `end` line.
- **`havne-cli devices`** lists the serial ports, CAN interfaces and J2534 adapters a URI can name. It ships in the Windows zip, the deb and the tarball.

**Core for your own programs**
- **A deb and a tarball** hold `havne-cli`, the static library and its C headers, with a CMake package (`find_package(ecuio)`, then `ecuio::core`) and a pkg-config file (`ecuio`). Before 1.0 a minor version may change the C ABI, so `find_package(ecuio 0.3)` takes any 0.3.x and no other.

**Debugging, and what's inside each download**
- **Debug symbols:** `havne-0.3.4-windows-x64-symbols.zip` holds the PDBs of `havne.exe`, `havne-cli.exe` and both J2534 helpers ([ADR-0034](https://github.com/erickramer42/havne/blob/main/docs/adr/0034-debug-symbols-and-probes.md)), and on Linux `havne-cli`'s debug info ships as `havne-core-dbgsym` and a `-debug` tarball, found by `gdb` and `perf` by build ID. A crash dump or a profile reads against the source.
- **An SBOM:** `havne-0.3.4.spdx.json` (SPDX 2.3) lists what each download contains: Qt and the other libraries it bundles, at their versions.
- **Reproducible Linux downloads:** the deb and the tarballs build to the same bytes from the same source, wherever they're built, so anyone can rebuild them from this tag and compare; CI checks it on every change. The AppImage does too when it's built on the same Ubuntu packages.

**Fixes**
- **A sleep on Linux or Android is a gap** on Live, in a recording's times and in `havne-cli`'s stream, instead of the values on either side being joined as if nothing had been missed; values read before the sleep dim as stale at the wake ([ADR-0033](https://github.com/erickramer42/havne/blob/main/docs/adr/0033-session-time-counts-sleep.md)). The activity log, and a recording's `events.log`, say "Asleep for N s: nothing was read meanwhile". Windows, macOS and iOS already counted a sleep.
- **A replay of a recording cut short after it was opened** says "Replay stopped" with the frames it sent, as one whose rows turned bad does, instead of going quiet as if finished. Rows added to a recording while it plays (one still being written) wait for the next replay, so its frame count and length stay as shown at the start.
- The build option `QTTUNE_BUILD_CORE_ONLY`, the name before the rename, is gone: use `HAVNE_BUILD_CORE_ONLY`.
- The full list is in the [CHANGELOG](https://github.com/erickramer42/havne/blob/main/CHANGELOG.md#034---2026-10-30).

## What's verified, and where

Havne's claims are tiered ([docs/testing.md](https://github.com/erickramer42/havne/blob/main/docs/testing.md)):

- **Every build** runs the full test suite on Windows, macOS and Linux in CI, plus sanitizers, fuzzing, clang-tidy, CodeQL, the load test on Windows and Linux, and a check of the C ABI against 0.3.3's. `havne-cli`'s output is compared with committed golden files on every platform. The Android and iOS apps are cross-built there; their tests don't run on a device.
- **Linux:** CI builds the AppImage on Ubuntu 24.04 and starts it offscreen; builds the core packages twice, varying the folder, clock, locale and more, and requires the same bytes; then installs them, runs `havne-cli` and builds a C program against them three ways. SocketCAN and the simulated car run against `vcan0`, sanitizers included, and the probes are traced with `bpftrace`. On a Windows machine's WSL, the AppImage ran on Ubuntu 26.04, Arch and Kali with a window (WSLg): the simulated car connected with recording on, every page drew and took input, and closing the window ended it.
- **A sleep:** one phone (Android 16) slept thirteen times in an 11-minute `mock://demo` session, and each sleep is a gap of its length on Live and in the recording, with its "Asleep" line ([session sheet](https://github.com/erickramer42/havne/blob/main/docs/bench-sessions/2026-10-29-android-2.md)). That run used a development build. A Linux machine's suspend hasn't been tried.
- **Not yet run:** the app on a Linux machine's own desktop, an ELM327 adapter on a Linux machine (the serial code is tested against a fake adapter on a pseudo-terminal), a real CAN controller, and a car through SocketCAN. This build itself hasn't connected to an adapter or a car; nothing has been run on a car since 0.3.3. iOS hasn't run on a device.

## Verifying the downloads

`SHA256SUMS.txt` holds every download's SHA-256, the debug files' and the SBOM's. Each download also carries a signed build provenance from this repository's release workflow, attached as `<download>.intoto.jsonl`. Check them with the GitHub CLI:

```
sha256sum -c --ignore-missing SHA256SUMS.txt
gh attestation verify havne-0.3.4-windows-x64.zip -R erickramer42/havne
gh attestation verify havne-0.3.4-android-arm64-v8a.apk -R erickramer42/havne
gh attestation verify havne-0.3.4-linux-x86_64.AppImage -R erickramer42/havne
gh attestation verify havne-core_0.3.4_amd64.deb -R erickramer42/havne
```

The SBOM is attested to the zip, the APK, the AppImage, the deb and the tarball: add `--predicate-type https://spdx.dev/Document/v2.3` to check it.

The APK is signed with Havne's release key, whose certificate SHA-256 is `fb4f415a1f6c0dc56ee54dcd454c29d2226bc293c7b4c978a9b9bc8e74c4210f` ([packaging/android/release-cert.sha256](https://github.com/erickramer42/havne/blob/main/packaging/android/release-cert.sha256)). With the Android SDK's build tools, `apksigner verify --print-certs havne-0.3.4-android-arm64-v8a.apk` prints it.
