Havne 0.3.5 reads a car's trouble codes and clears them, reads every standard Service 01 value a car supports, several at a time, and sends requests through native CAN interfaces on Linux, with fault injection and reply timing to test it all without a car. Read [DISCLAIMER.md](https://github.com/erickramer42/havne/blob/main/DISCLAIMER.md) before connecting it to a vehicle.

## Try it

**Windows**

1. Download `havne-0.3.5-windows-x64.zip` and unzip the whole folder.
2. Run `havne.exe`. The program isn't code-signed, so SmartScreen may stop it the first time: choose **More info**, then **Run anyway**.
3. In Settings, tick **Developer mode** under Display, then press the `mock://demo` preset under Adapter and **Connect**.

The zip's `README.txt` covers adapters and what each file is. `havne-cli.exe` is beside `havne.exe`: `havne-cli stream mock://demo --values --count 20` prints a simulated car's frames and values.

**Linux (x86_64, glibc 2.39 or later: Ubuntu 24.04 and newer, Debian 13, Fedora 40 and newer, Arch)**

1. Download `havne-0.3.5-linux-x86_64.AppImage`.
2. `chmod +x havne-0.3.5-linux-x86_64.AppImage`, then run it.
3. In Settings, tick **Developer mode** under Display, then press the `mock://demo` preset under Adapter and **Connect**.

It takes OpenGL, fonts and FUSE from the system; a minimal install may lack them. [docs/linux.md](https://github.com/erickramer42/havne/blob/main/docs/linux.md) says what to install, how to reach an adapter (serial permissions, Bluetooth, SocketCAN) and where Havne keeps its files.

For `havne-cli` and the core alone: `sudo apt install ./havne-core_0.3.5_amd64.deb`, or unpack `havne-core-0.3.5-linux-x86_64.tar.gz` anywhere.

**Android 12 or later (64-bit ARM)**

1. On the phone, download `havne-0.3.5-android-arm64-v8a.apk` and open it. Android asks to let your browser or file manager install apps the first time; Play Protect may offer to scan an app from outside Google Play.
2. Open Havne. In Settings, tick **Developer mode** under Display, then press the `mock://demo` preset under Adapter and **Connect**.

A later release installs over this one and keeps its settings and recordings. A Havne built by CI or from source carries another key, so uninstall it first.

## What's new since 0.3.4

**Trouble codes**
- **Reading** ([ADR-0037](https://github.com/erickramer42/havne/blob/main/docs/adr/0037-reading-trouble-codes.md)): a session that asks the car (`obd2` or `uds-generic`, through a J2534 or ELM327 adapter) reads each ECU's check-engine light, its stored, pending and permanent codes, its readiness monitors and the freeze frame stored with a code, once at connect, taking turns with the live values. `?diagnose=0` leaves them out.
- **A Diagnostics page** (after Live in the sidebar, "Codes" among a narrow window's tabs) shows each ECU's light, its codes by list, which monitors are complete and the freeze frame's values; **Read again** asks once more. The activity log gets a line per ECU per read, so a recording keeps the codes as they were, and `havne-cli stream` writes a `diagnostics` line.
- **Clearing** ([ADR-0038](https://github.com/erickramer42/havne/blob/main/docs/adr/0038-clearing-trouble-codes.md)): **Clear codes...** asks first, saying what a clear erases and what it keeps. The report is saved to a file before anything is sent, and each ECU is cleared only once it reports its engine stopped, then read again. Not yet run on a car.
- The simulated car (`mock://`) has codes, readiness and a freeze frame, and starts each loop with its engine stopped, so all of it shows with no hardware.

**Every standard Service 01 reading**
- **130 signals** ([ADR-0039](https://github.com/erickramer42/havne/blob/main/docs/adr/0039-full-service01-coverage.md)): the `obd2` profile reads every linear field of SAE J1979's Service 01 table (both banks' fuel trims, every oxygen sensor, wide-range lambda, fuel pressure, catalyst temperatures, torque, run times and distances among them) and asks each car only for the ones it has. Fast-changing readings are asked twice for each slow one.
- **Several PIDs per request:** with the probe on, a request carries up to six PIDs, so each signal refreshes more often; on the test car through an OBDLink MX+, four to five times as often. A car that mishandles them is asked one PID per request for the session. `?pack=0` turns it off.
- **Live shows what the car has:** it lists only the signals the ECU supports and sends, with a line saying how many it left out (the Dashboard and recordings keep every signal), plots the six best ranked signals the car has when a session starts, and shows the last 10, 30, 60 or 120 s.
- Imperial units cover the new units: Pa as inH2O, L/h as gal/h and `N·m` as `lb·ft`.

**SocketCAN requests**
- **`obd2` and `uds-generic` on a native CAN interface** ([ADR-0040](https://github.com/erickramer42/havne/blob/main/docs/adr/0040-socketcan-requests-isotp.md)): `socketcan://can0?profile=obd2&baud=500000`, with ISO-TP done in core and the same query keys as `j2534://` and `elm327://`. Havne sends only through a controller brought up to stop at once on a fault, sends nothing more after a CAN error on its first request, and gives the `ip link` commands that fix a refusal. Run on Linux's virtual CAN bus only: not yet through a real controller or on a car.

**Testing without a car**
- **Fault injection on a replay** ([ADR-0041](https://github.com/erickramer42/havne/blob/main/docs/adr/0041-replay-fault-injection.md)): `replay://<recording>?faults=drop:5,overflow:1,corrupt:1,truncate:2,stall:1:500` plays a recording with frames dropped, lost to an overflow, corrupted, cut short or held back, the same each run from `?seed=`, and says what the faults did.
- **Reply timing per request** ([ADR-0042](https://github.com/erickramer42/havne/blob/main/docs/adr/0042-reply-timing.md)): a requesting session measures each PID's answers, refusals and timeouts, its reply latency and its refresh interval at P50, P99 and P99.9. A recording keeps them in `latency.csv`, `havne-cli stream` writes `timing` lines, and the activity log sums them up at the disconnect.

**For programs on the C ABI**
- New calls report what core judges, so a program gets what the app shows: the signals a car's replies come without (`ecuio_session_get_absent_signals`) and those its ECU doesn't support (`ecuio_session_get_unsupported_signals`), the VIN from an identification report (`ecuio_identity_vin`), the supported-PID count (`pids_supported`, `pids_through`), packed replies that didn't split, a replay's fault counts, reply timing (`ecuio_session_get_timing`), and each signal's plot rank.

**iPhone, for testers**
- Each CI run builds an unsigned iPhone app that a tester installs with a sideloading tool and their own Apple ID ([docs/ios.md](https://github.com/erickramer42/havne/blob/main/docs/ios.md)). It isn't a release download.

**Changes and fixes**
- A release's page opens with a table of each platform's download, and one provenance file, `havne-0.3.5.intoto.jsonl`, covers every download.
- The Log page's **Activity | Frames** switch (developer mode) stays in place when the view changes.
- Live's time axis no longer draws its captions over one another on a narrow window.
- A replay whose faults dropped frames still ends, with the "Replay finished" line and `havne-cli`'s end line.
- The full list is in the [CHANGELOG](https://github.com/erickramer42/havne/blob/main/CHANGELOG.md#035---2026-11-01).

## What's verified, and where

Havne's claims are tiered ([docs/testing.md](https://github.com/erickramer42/havne/blob/main/docs/testing.md)):

- **Every build** runs the full test suite on Windows, macOS and Linux in CI, plus sanitizers, fuzzing (ISO-TP's reassembly among the targets), clang-tidy, CodeQL, the load test on Windows and Linux, and a check of the C ABI against 0.3.4's. The Android and iOS apps are cross-built there; their tests don't run on a device.
- **Against the fakes and the simulated bus:** trouble codes are read through the fake J2534 adapter (in both the 64-bit and the 32-bit helper process), the fake ELM327 and the simulated car, and cleared on the fakes and the simulated car. SocketCAN requests run on Linux's `vcan0` against an ECU answering through the kernel's own ISO-TP, core's ISO-TP held to the kernel's, and against the test car's recording answering as the ECU with its replies broken at the ISO-TP level.
- **On the test car** (2026-10-31, development builds before this release): the full `obd2` set through both adapters, an OBDLink MX+ on a phone (Android 16) and the OBDX Pro VX over J2534 on a laptop. The probe kept the 43 PIDs the car's bitmaps list and Live hid the 81 signals of the rest; the rate classes refreshed near their estimates; the trouble-code read worked on an ECU with no codes stored, and both adapters' reports agreed. Through the MX+, several PIDs per request: every pack answered in J1979's form, each signal four to five times as often ([MX+](https://github.com/erickramer42/havne/blob/main/docs/bench-sessions/2026-10-31-elm327-vehicle.md), [packing](https://github.com/erickramer42/havne/blob/main/docs/bench-sessions/2026-10-31-elm327-vehicle-2.md), [VX](https://github.com/erickramer42/havne/blob/main/docs/bench-sessions/2026-10-31-vehicle.md)).
- **These downloads, checked as published** (and in a full dry run, `v0.3.5-rc1`, before them): the checksums and provenance verify for every file, and the SBOM's attestation for the zip, the APK, the AppImage, the deb and the tarball; the zip holds the app, `havne-cli`, both J2534 helpers, the disclaimer, license and readme, and the symbols zip their four PDBs; the APK is version 0.3.5, not debuggable, and signed with the pinned release key. On Linux (Ubuntu 26.04 under WSL) the deb's `havne-cli` streamed the simulated car, its debug info matched by build ID, and the AppImage started. The release APK itself hasn't run on a phone.
- **Not yet run:** a clear on a car, and a car with a code stored; several PIDs per request through the VX; SocketCAN through a real CAN controller or on a car; the new values beside a second scan tool's. This build itself hasn't connected to an adapter or a car. The iPhone app hasn't run on a device.

## Verifying the downloads

`SHA256SUMS.txt` holds every download's SHA-256, the debug files' and the SBOM's. One signed build provenance from this repository's release workflow covers every download, attached as `havne-0.3.5.intoto.jsonl`. Check them with the GitHub CLI:

```
sha256sum -c --ignore-missing SHA256SUMS.txt
gh attestation verify havne-0.3.5-windows-x64.zip -R erickramer42/havne
gh attestation verify havne-0.3.5-android-arm64-v8a.apk -R erickramer42/havne
gh attestation verify havne-0.3.5-linux-x86_64.AppImage -R erickramer42/havne
gh attestation verify havne-core_0.3.5_amd64.deb -R erickramer42/havne
```

Those read GitHub's attestation store; add `--bundle havne-0.3.5.intoto.jsonl` to check against the attached file instead.

The SBOM, `havne-0.3.5.spdx.json`, is attested to the zip, the APK, the AppImage, the deb and the tarball: add `--predicate-type https://spdx.dev/Document/v2.3` to check it.

The APK is signed with Havne's release key, whose certificate SHA-256 is `fb4f415a1f6c0dc56ee54dcd454c29d2226bc293c7b4c978a9b9bc8e74c4210f` ([packaging/android/release-cert.sha256](https://github.com/erickramer42/havne/blob/main/packaging/android/release-cert.sha256)). With the Android SDK's build tools, `apksigner verify --print-certs havne-0.3.5-android-arm64-v8a.apk` prints it.
